# GitHub 开源项目健康度分析 Dashboard — Reference Brief

> 状态：设计前参考门禁；访问与复核日期：2026-07-12；范围：仅形成 Reference Brief，不生成 Dashboard、线框图、视觉稿或代码。

## 1. 当前任务与边界

- **交付物**：一个面向单个 GitHub 开源仓库的健康度分析 Dashboard 的参考依据与可执行设计契约。
- **任务标签**：`Dashboard`、`open-source health`、`repository analytics`、`maintainer decision support`、`trend + checklist + risk states`。
- **工作使用场景（待确认）**：维护者或 OSPO 在周期性项目复盘中，先定位风险，再下钻到指标证据和整改动作。
- **工作目标受众（待确认）**：仓库维护者、项目负责人、OSPO；若主要受众改为“技术选型者/依赖方”，合规、安全和可持续性权重需要重新定义。
- **范围锁定**：题目使用单数“一个项目”，本 Brief 先按“单个公开 GitHub 仓库”组织；组织级、多仓组合、私有仓库和跨项目排行榜不在本轮范围。
- **技术栈/目标环境**：未提供，不指定 ECharts、D3、React 或其他实现栈；只给出与库无关的图表和状态契约。
- **品牌与风格**：未提供品牌、模板或参考图。建议采用克制、中性、数据优先的开发者工具视觉，但不复制 GitHub、CHAOSS 或 OSS Compass 的品牌资产。
- **不可自行决定**：健康总分公式、指标权重、红黄绿阈值、默认时间窗、机器人过滤口径、时区、数据刷新 SLA、是否允许项目间比较。
- **本轮参考维度**：信息架构、指标模型、筛选与上下文、图表选型、状态与异常、行动闭环、数据/许可边界。

## 3. 核心参考分析

### 3.1 GitHub Community Standards：从状态展示走向整改动作

- **具体案例**：[`pingcap/ossinsight` Community Standards 实页](https://github.com/pingcap/ossinsight/community)；[GitHub Community Profile 官方说明](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories)。
- **相关性**：这是 GitHub 仓库内真实的“健康检查清单”，直接展示项目治理文件是否齐全，并把缺口连接到补救动作。
- **事实（来源明确陈述）**：Community Profile 会检查 README、CODE_OF_CONDUCT、LICENSE、CONTRIBUTING 等推荐文件；维护者可对缺失项执行添加/设置动作。
- **视觉/结构观察（本轮浏览器检查）**：
  - 左侧使用稳定的 Insights 分区导航，当前项清楚高亮。
  - 主区先显示整体完成进度，再用逐行清单呈现“已满足/待补齐”；状态同时使用图标、文字和颜色，而不是只靠颜色。
  - 缺失项在同一行提供上下文动作，例如设置安全策略，减少“看见风险但不知道下一步”的断点。
- **推断**：健康 Dashboard 不应只展示分数；至少要有一个“健康卫生项/治理就绪度”区，把每个风险连接到证据与可执行动作。
- **采用**：分区导航、进度 + 明细清单、非颜色单一编码、行内整改动作。
- **不采用**：GitHub 的商标、专有导航样式、原文案、完整构图；也不把文件存在性当作全部项目健康。
- **项目转译**：在“项目基础与治理”模块展示 README、许可证、贡献指南、行为准则、安全策略、Issue/PR 模板等；每项给出检测依据、状态和整改入口。
- **许可/使用条件**：GitHub Docs 仓库内容标注 [CC BY 4.0](https://github.com/github/docs/blob/main/LICENSE)。本项目只提炼通用模式，不复制截图、商标或产品 UI 资产；GitHub 产品界面的品牌权利不视为随文档许可一并开放。

### 3.2 GitHub Pulse 与 Metrics API：统一时间上下文，并显式处理数据未就绪

- **具体案例**：[Using Pulse to view a summary of repository activity](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/using-pulse-to-view-a-summary-of-repository-activity)；[REST API endpoints for metrics](https://docs.github.com/en/rest/metrics)；[repository statistics 端点说明](https://docs.github.com/en/rest/metrics/statistics)。
- **相关性**：Pulse 说明仓库活动概览如何围绕同一时间段组织 PR、Issue 与提交；Metrics API 揭示真实实现必须面对的缓存、异步计算、权限和数据边界。
- **事实（来源明确陈述）**：
  - Pulse 支持选择时间段，并汇总开放/合并 PR、开放/关闭 Issue 和提交活动。
  - 部分仓库统计在未缓存时会先返回 `202` 并异步计算；部分统计还存在仓库规模限制或统计排除规则。
- **视觉/结构观察（本轮浏览器检查）**：官方文档使用清楚的侧栏层级和任务导向说明；实际公开 Pulse 路由在无登录的本轮 headless 会话中未完成主区加载，因此未把该空白结果当作产品视觉证据。
- **推断**：全局时间窗必须对所有指标一致生效；每个指标还必须显示数据更新时间、覆盖范围与数据质量状态，避免把“尚未计算/无权限”误判为零。
- **采用**：全局时间窗、统一上下文、数据来源/更新时间、局部重试和等待状态。
- **不采用**：把空白主区当作理想空状态；不在未核实统计口径时混合 GitHub 页面数值与外部事件库数值。
- **项目转译**：顶栏展示仓库、时间窗、时区、是否排除机器人、最后更新时间；图表级状态区分 `loading`、`no events`、`partial coverage`、`permission required`、`rate limited`、`stale`、`error`。
- **许可/使用条件**：同 3.1。API 文档可用于事实与交互约束；不复制 GitHub 产品代码或视觉资产。

### 3.3 CHAOSS Starter Project Health：用可解释的四项指标替代“热度即健康”

- **具体案例**：[Starter Project Health Metrics Model](https://chaoss.community/kb/metrics-model-starter-project-health/)。
- **相关性**：该模型专门回答“如何以最少指标开始理解开源项目健康”，与本 Dashboard 的主题直接一致。
- **事实（来源明确陈述）**：该模型给出四个起始指标：Time to First Response、Change Request Closure Ratio、Contributor Absence Factor、Release Frequency；同时强调不同项目需要结合自身情境解读，机器人活动也会影响部分指标。
- **视觉/结构观察（本轮浏览器检查）**：页面先解释“为什么重要”和用户故事，再列指标，随后给出数据洞察与情境限制；指标不是脱离语境的 KPI 列表。
- **推断**：首屏核心应围绕“响应、吞吐/积压、人员韧性、发布节奏”四个可解释维度，而不是 stars、forks 或提交数的简单加权总分。
- **采用**：四项起始指标、指标解释、项目内趋势、机器人过滤提示、情境化阈值。
- **不采用**：未经项目验证的固定阈值；跨项目绝对排名；把任何单一指标标成“最终健康结论”。
- **项目转译**：四张核心卡均包含“当前值、相对自身历史的变化、口径、覆盖度、下钻入口”；只有在指标契约明确后才显示健康状态色。
- **许可/使用条件**：CHAOSS website 仓库标注 [MIT License](https://github.com/chaoss/website/blob/main/LICENSE)。本 Brief 只引用指标名称与抽象规则，不复制网站图像或品牌元素；实际指标实现仍需确认数据伦理、隐私与平台条款。

### 3.4 OSS Compass Dashboard：维度导航、成组趋势卡与轴缩放控制

- **具体案例**：[OSS Compass feature update — Y-axis Scaling](https://oss-compass.org/blog/2023/07/28/y-axis-scaling/y-axis-scaling/)。
- **相关性**：该页展示一个专门面向开源社区健康评估的项目 Dashboard，并解释趋势图 Y 轴缩放为何需要成为用户可见的控制项。
- **事实（来源明确陈述）**：OSS Compass 为已分析项目生成专属 Dashboard，以图表展示项目整体趋势和评估指标变化；其设置中允许用户切换 Y 轴缩放。
- **视觉/结构观察（本轮浏览器检查）**：
  - Dashboard 截图采用左侧维度树 + 右侧同类指标卡的主结构。
  - 顶部保留项目身份、时间段和设置；同一维度下并排展示趋势图，便于在共享时间轴下比较。
  - 轴缩放被放在设置入口，并有明确开关状态，说明视觉缩放可能改变读者对变化幅度的感受。
- **推断**：同一健康维度的指标应成组展示；任何非零起点、缩放、归一化或百分制转换都必须对用户透明，并允许查看原始口径。
- **采用**：维度导航、共享筛选上下文、成组趋势卡、轴/量纲设置透明化。
- **不采用**：照搬其视觉品牌、页面布局或评分模型；不默认启用可能夸大波动的截断 Y 轴。
- **项目转译**：趋势卡标注轴范围和单位；若允许缩放，提供“从零/聚焦变化”显式切换，并在导出中保留选择；默认值由产品方确认。
- **许可/使用条件**：OSS Compass `compass-web` 代码仓库为 [AGPL-3.0](https://github.com/oss-compass/compass-web/blob/main/LICENSE)。博客截图、商标和品牌资产不假设受同一许可覆盖；本项目仅提炼交互原则，不复用其代码、截图或品牌素材。该案例文章发布于 2023 年，当前产品界面可能已有变化，因此只把已核实的交互原则作为证据。

### 3.5 From Data to Viz：趋势用折线，矩阵概览才用热力图

- **具体案例**：[Line chart](https://www.data-to-viz.com/graph/line.html)；[Heatmap](https://www.data-to-viz.com/graph/heatmap.html)。
- **相关性**：为健康指标的时间趋势和活动矩阵提供图型 Gate，防止“为了丰富版面而选图”。
- **事实（来源明确陈述）**：折线图适合展示一个或少数数值变量随有序时间的演化；线条过多会造成不可读的“意大利面图”，双轴也容易误导。热力图适合用颜色查看矩阵总体模式，但不适合读取精确单点，且常需要归一化和清楚色标。
- **视觉/结构观察（本轮浏览器检查）**：两个页面都先给定义与示例，再说明适用场景、变化形式和常见错误；这比从图库直接挑“好看图表”更适合做选型门禁。
- **推断**：核心趋势页应优先少量折线；活动热力图只用于“日期/星期 × 小时”等规则时间矩阵，不能把不同量纲的健康指标直接涂成一张颜色矩阵。
- **采用**：时间趋势折线、少系列限制、明确轴与单位、热力图色标和精确值补充。
- **不采用**：双 Y 轴、过多折线、无归一化说明的热力图、仅靠颜色传达精确值。
- **项目转译**：健康趋势每图最多突出 1–3 个系列；更多系列改为筛选或 small multiples。热力图保留图例、悬停数值和表格替代视图。
- **许可/使用条件**：`data_to_viz` 仓库标注 [MIT License](https://github.com/holtzy/data_to_viz/blob/master/LICENSE)。仍不复制其图像、数据集或代码；只采用图型选择规律。

## 4. 多来源综合：6 条可执行规律

1. **先回答“哪里需要行动”，再提供探索。** 首屏顺序为：项目身份与数据新鲜度 → 四个健康维度摘要 → 风险/待办队列 → 趋势与证据下钻。stars、forks、watchers 只作为背景热度，不占健康结论主位。
2. **核心健康模型必须可解释、可拆解。** 以响应时间、变更请求闭环、贡献者集中风险、发布节奏为起点；不在指标定义、权重和阈值未确认时输出一个不透明总分或跨项目排名。
3. **一个筛选上下文贯穿整页。** 仓库、时间窗、时区、机器人过滤和数据更新时间必须可见；局部图表若使用不同范围，要在卡片标题区显式标注，不能静默偏离全局筛选。
4. **图型由数据关系决定。** 趋势用少量折线；离散排名用排序条形；贡献者集中度用排序贡献条并突出达到 50% 的最小人数；热力图只用于规则矩阵概览。禁用双轴、仪表盘堆叠和无口径雷达图。
5. **颜色表示已定义的语义，不替代文字。** 只有阈值经过指标契约确认后才使用绿/黄/红；所有状态同时给出图标、文字、数值和原因。未定义阈值时使用中性“需关注/数据不足”，不伪造精确健康判断。
6. **每个风险必须闭环到证据和动作。** 卡片或清单项应提供“为什么触发、受影响时间段、原始事件/列表、建议动作”；同时覆盖加载、无事件、部分覆盖、权限不足、限流、陈旧与错误状态，避免将采集失败显示为健康或零。

## 5. 当前项目落实地图

| 规律 | 页面/组件 | 设计转译 | 下游验收证据 |
|---|---|---|---|
| 1 | 顶栏 + 决策摘要 + 行动队列 | 顶栏显示仓库与数据新鲜度；四维摘要之后立即列出高优先级风险，不让用户先滚过大量图表 | 5 秒内可回答“当前最值得处理的 1–3 个问题是什么”；stars/forks 不作为健康主卡 |
| 2 | 四维健康卡 | 响应、变更闭环、贡献者韧性、发布节奏；每卡含值、趋势、口径、覆盖度和下钻 | 任一卡都能打开指标定义与原始证据；未确认权重时页面无综合分 |
| 3 | 全局筛选条 | 仓库、时间窗、时区、机器人过滤；显示最后更新时间和数据来源 | 改变筛选后所有卡同步更新；例外卡明确标注自己的时间范围 |
| 4 | 趋势区、韧性区、活动下钻 | 折线不超过 3 个突出系列；贡献者用排序条；热力图只放在活动模式下钻 | 图标题包含单位/时间粒度；无双轴；热力图有图例、悬停值与表格替代 |
| 5 | 状态 token 与图表注释 | 图标 + 文本 + 数值 + 颜色；阈值和基准可追溯 | 灰阶或色觉缺陷情境下仍能识别状态；每个红黄状态可查看触发规则 |
| 6 | 风险列表、清单、图表状态 | 风险行含原因、证据、动作；图表覆盖七类数据状态 | 用模拟数据逐一验收 loading/empty/partial/permission/rate-limit/stale/error，且零值不与缺失混淆 |

## 6. 建议的信息架构

1. **项目头部**：仓库名称、描述/主语言（背景信息）、时间窗、时区、机器人过滤、数据更新时间、覆盖度。
2. **健康摘要**：四张可解释指标卡，不使用未经定义的综合分。
3. **优先行动**：按影响与证据可信度排序的风险/缺口列表；含治理清单动作。
4. **趋势与流动**：响应时间、变更请求进入/关闭、发布事件；所有图共享时间轴。
5. **社区韧性**：贡献者集中度、活跃/新增/回归贡献者；个人层面只展示完成决策所需信息。
6. **项目基础与治理**：Community Standards 风格的检查项、检测依据、状态与整改入口。
7. **数据质量与口径**：端点来源、更新时间、覆盖范围、机器人规则、缺失/限流/权限说明。

## 7. 状态与交互契约

| 状态 | 必须展示 | 禁止做法 |
|---|---|---|
| Loading | 保留卡片几何的 skeleton、正在计算说明、可选预计/重试信息 | 空白主区或把旧值伪装成当前值 |
| No events | “当前时间段无事件”、所用筛选、扩大时间范围动作 | 显示为 `0 = 健康` |
| Partial coverage | 缺失来源/时间段、已覆盖比例、受影响指标 | 无提示地计算综合结论 |
| Permission required | 所需访问级别、登录/授权动作、仍可见的公开数据 | 暴露凭证或暗示用户粘贴 token 到页面文本区 |
| Rate limited / computing | 状态原因、重试/刷新时机、最后可用快照时间 | 无限转圈或频繁自动重试 |
| Stale | 最后更新时间、刷新 SLA、手动刷新入口 | 只显示数值不显示时间 |
| Error | 局部错误、可重试、问题标识；其他模块继续可用 | 一个图失败导致整页空白 |

## 8. 明确不采用

- **stars/forks = 健康**：它们表示关注度或传播，不足以回答响应、积压、韧性和发布节奏。
- **不透明综合分、仪表盘和雷达图**：在公式、权重、阈值未确认时会制造虚假的精确性。
- **跨项目排行榜**：CHAOSS 强调指标需结合项目情境；本轮也没有项目类型、生命周期或规模归一化口径。
- **双 Y 轴或静默截断 Y 轴**：容易放大或扭曲变化；任何缩放都必须显式、可还原。
- **地理/公司分布作为首屏健康指标**：与维护行动的直接关系弱，并带来隐私和数据伦理风险。
- **复制参考品牌/构图/代码**：不复制 GitHub、CHAOSS、OSS Compass、From Data to Viz 的商标、截图、原文案、代码或完整布局。
