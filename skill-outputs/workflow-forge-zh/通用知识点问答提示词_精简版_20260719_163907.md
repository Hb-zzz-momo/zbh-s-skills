# 通用知识点问答提示词（精简版）

```text
请把下面的知识点解释给零基础读者：

- 问题：[填写问题]
- 项目或业务背景：[可选]
- 已知材料或证据：[可选]
- 回答深度：[精简 / 标准 / 深入，默认标准]

请遵守以下规则：

1. 开头先用一个具体生活场景建立直觉，再介绍抽象定义。场景必须说明“谁在做什么、目标是什么、哪里可能出错”，并立即映射到真实技术对象。

2. 全文只使用同一个人物、业务对象、动作和类比体系。如果没有真实项目背景，明确说明这是用于解释的假设例子，不得当成项目事实。

3. 类比后用一句话定位概念：它位于哪两个环节之间、接收什么输入、解决什么问题、输出什么结果。

4. 在详细解释前先展示一条完整且最小的路线图：

   起点 → 节点1 → 节点2 → 最终结果

5. 主链中的每个节点必须满足：

   一个当前矛盾
   → 一个核心动作或机制
   → 一个核心产物
   → 该产物成为下一节点的必要输入

   如果一个节点同时讨论多个独立问题或产生多个独立产物，必须拆分节点；如果内容不是下一步的必要条件，把它移到“补充理解”，不要放进主链。

6. 每次进入新节点，只显示一行位置提醒：

   链路位置：[上游] → 【当前节点】 → [下游]

   随后用连续自然语言说明：因为上一节点产生了什么，所以当前步骤才能发生；当前只解决哪个矛盾，形成哪个核心产物；下一节点为什么必须使用该产物。

   不要重复输出“承接上一步、本步解决、本步产物、交给下一步”等填表式栏目，也不要在栏目下继续堆清单。

7. 专业术语只在对应节点首次出现时解释。首次出现时给出英文全称、中文名称、在当前节点中的作用和当前实例；不要在开头集中罗列术语。

8. 链路超过4个节点时，每经过2至3个节点增加一次“到目前为止”小结，说明已经形成什么核心产物、还缺什么才能达到最终目标。

9. 项目型回答必须区分：

   - 事实：代码、文档、测试或数据直接显示的内容；
   - 推理：由事实得到的含义；
   - 评价：基于成本、收益和风险作出的判断。

   没有项目证据时，明确写“以下仅作通用解释”或“待项目证据确认”。类比不能作为事实证据。

10. 成稿前执行删除节点测试：逐个删除主链节点。如果删除某个中间节点后，下一节点仍能自然出现并获得所需输入，该节点不是必要主链，应删除、合并或移到补充部分。删除终点后如果最终目标仍然成立，终点也不是必要节点。

11. 最后回到开头的同一个实例，用“输入 → 处理 → 核心产物 → 下游决定”重新走完整条链，并说明当前应该先做什么、哪些工作应当延后。

推荐输出结构：

# [知识点]小白解析

## 先进入一个具体场景
[贯穿全文的故事和角色映射]

## 一句话定位
[链路位置、输入、问题和输出]

## 全程路线图
[起点 → 节点1 → 节点2 → 最终结果]

## 第1站：[单一动作]
链路位置：【起点】 → [节点1] → [节点2]
[连续因果叙述：一个矛盾、一个动作、一个核心产物、下一步必要输入]

## 第2站：[单一动作]
链路位置：[起点] → 【节点1】 → [节点2]
[继续同一实例和因果链]

## 到目前为止（长链路时使用）
[已形成什么、还缺什么]

## 补充理解（仅放非主链内容）
[术语补充、风险、例外或扩展知识]

## 最终理解
[回到开头实例，复述输入 → 处理 → 核心产物 → 下游决定]

请直接输出最终回答，不要解释你使用了哪些提示词规则。
```
