# 通用知识性问答提示词：小白场景与状态逻辑链版

> 用途：让 AI 在回答技术、工程、架构、项目分析及其他知识性问题时，既让零基础读者看懂，又正确表达串行、并行、证据和前置条件之间的关系。

## 可直接复制的提示词

```text
请用“小白能够理解并复述”的方式回答我的知识性问题。

不要先罗列术语，也不要把所有信息强行排成一条直线。请先判断信息之间的真实关系，再组织答案。

一、先建立一个贯穿全文的具体场景

1. 在任何抽象定义之前，先用一个生活类比或具体人物故事建立直觉。
2. 场景必须包含：谁正在做什么、目标是什么、遇到了什么问题。
3. 随后把场景中的角色映射到真实概念。
4. 全文沿用同一个人物、对象和目标，不要中途更换例子或比喻体系。
5. 如果没有真实项目背景，明确说明这是用于解释的假设例子，不能把它写成事实。

二、先判断每条信息在本题中的关系

围绕本题的目标状态，把信息判断为以下角色之一：

- 原因：直接促成后续状态；
- 证据：用于证明某个判断；
- 前置条件：达到目标必须具备，但不一定由前一步产生；
- 结果：前面状态造成的后果；
- 动作：用于改变当前状态的措施。

分类不是永久标签。必须说明“这条信息相对于哪个判断，为什么属于这个角色”。

三、建立状态变化主链

主链节点必须写成“主体发生了什么变化”或“当前处于什么状态”，不能只写技术名词。

错误示例：

接口 → OpenAPI → 文件存储 → 可观测性

正确示例：

规划的功能范围快速增加
→ 实际完成能力没有同步增加
→ 已完成部分仍未达到稳定交付标准
→ 用户无法走通一条完整流程

每条箭头后都要用一句白话解释：

- 前者为什么会引出后者；
- 二者属于因果、约束、输入输出，还是状态继续恶化；
- 如果只能说明时间先后或主题相近，就不能使用因果箭头。

四、把证据放回它所证明的状态

数字、文件、接口、测试结果和技术对象通常是证据或实现条件，不要自动把它们升级为主章节。

例如：

- “189 个目标接口、403 个页面”用于证明规划范围很大；
- “25 个接口已接入”用于证明实际完成度较低；
- 它们不应成为三条互不相干的主链节点。

说明每条证据：它证明哪个状态、能证明到什么程度、不能代表什么。

五、正确表达并行关系

如果多个事项共同服务于同一个目标，但没有先后因果，就把它们放在同一个状态节点下。

必须说明：

1. 它们共同服务于什么目标；
2. 每一项分别解决目标中的哪一部分；
3. 它们属于哪种关系：
   - 独立共需：彼此不产生对方，但目标要求全部具备；
   - 相互耦合：一项会影响另一项的效果；
   - 互为替代：满足其中一种即可；
4. 为什么没有把它们写成前后因果。

例如正式接口说明、真实数据保存和错误定位能力，可能共同服务于“稳定交付”。它们可以并行补齐，不能写成“接口说明导致文件存储，文件存储又导致错误定位”。

六、让局部例子始终回到整体主链

进入某个术语、模块或例子前，先提醒：

“下面这个例子用于解释或证明主链第 N 个状态。”

例子结束后必须回扣：

“因此，这个例子让我们确认了什么状态；这个状态为什么会继续引出下一状态。”

不能讲完局部模块后直接切换话题。长链超过四个节点时，每两到三个节点增加一次“到目前为止”小结。

七、术语只在主链需要时解释

术语首次出现时说明：

- 英文全称和中文名称；
- 一句白话含义；
- 它在当前场景中具体负责什么；
- 一个最小例子。

不要先建立大段术语百科，再补概念之间的关系。

八、让解决链反向对应诊断链

先写清诊断链，再设计解决动作。每个动作必须说明：

- 它要改变诊断链中的哪个状态；
- 执行后预期变成什么状态；
- 用什么真实证据判断已经改变；
- 它必须串行执行，还是可以与其他动作并行。

例如诊断链为：

范围过大 → 完成度不足 → 正式化不足 → 用户流程未闭合

解决链应当是：

冻结新增范围
→ 选择一条具体用户流程
→ 并行补齐该流程的正式运行条件
→ 让真实用户走通并验证
→ 再决定是否扩展范围

不要只给出“完善接口、完善存储、完善监控”这样的并列建议。

九、推荐输出结构

1. 具体场景和角色映射；
2. 一句话结论；
3. 完整状态变化路线图；
4. 按状态逐站解释：上一状态为何引出当前状态、证据是什么；
5. 在对应状态下解释并行条件和局部例子；
6. 当前实际状态：区分计划、文档、代码、测试和运行结果；
7. 反向对应的解决链和验收证据；
8. 回到开头场景，用一段话完成最终闭环。

成稿不要机械重复“输入、输出、承接上一步、交给下一步”等固定栏目。关系简单时用自然段说明，只有确实能提高理解时才使用列表或路线图。

十、回答前自检

- 是否先给了一个零基础读者能理解的具体场景？
- 全文是否始终使用同一个实例？
- 主链节点是否都是状态判断，而不是技术名词？
- 每条箭头是否说明了真实关系？
- 指标是否放回它所证明的状态？
- 并行项是否说明共同目标和彼此关系？
- 局部例子是否在开始和结束时回扣主链？
- 删除任一主链状态后，后续是否仍能自然推出？如果可以，应删除或降为支撑信息。
- 是否错误地把证据或并行前置条件拿去做了主链删除测试？
- 每个核心问题状态是否都有对应动作和验收证据？
- 最终结论是否区分事实、推理和评价？

现在请回答这个问题：

[在这里填写问题、项目背景和已有数据]
```

## 使用说明

- 普通知识概念：保留场景、最小状态链、术语和最终闭环，可缩短证据与解决部分。
- 项目分析或架构审计：完整使用状态主链、证据归位、并行条件和反向解决链。
- 只问“在哪里实现”：仍先给场景，再沿“问题状态 → 机制介入位置 → 执行位置 → 结果如何约束下游”解释，不要只列平台和文件名。

## 最小验收标准

一份合格回答应让读者能够复述：

```text
现在处于什么状态
→ 为什么变成这样
→ 哪些事实证明这一判断
→ 哪些条件共同决定目标能否实现
→ 下一步用哪些动作改变状态
→ 如何确认问题真的解决
```
