## Decision D-001：扩展现有决策链，不新建同义 Skill

- 问题与约束：需要让决策理由贯穿方案选择、实现修改、函数注释、评审和交付；同时遵守最少 Skill 路由与现有职责边界。
- 决策标准（优先级顺序）：可触发性；端到端可验收；与现有职责一致；上下文和维护成本；是否形成可阻断门禁。
- 依据：现有 `documentation-and-adrs` 已负责 why 与 ADR；`engineering-skill-flow-zh` 已覆盖 Solution Gate、Main Build、Review、Ship；`code-review-and-quality` 已是合并前门禁。

| 方案 | 优点 | 缺点 | 风险 | 依据 | 裁决 |
|---|---|---|---|---|---|
| A. 只补 `documentation-and-adrs` | 改动最小、职责集中 | Main Build 不一定加载，缺少强制验收 | 规则存在但执行漏掉 | 当前工程路由只在 Design/Ship 默认加载该 Skill | CAUTION |
| B. 新建独立 rationale guardrail | 边界显式、可单独触发 | 与 ADR Skill 重叠，增加发现和路由成本 | 同义规则漂移 | Skill 维护规则要求最少必要组合，且现有职责已存在 | BLOCK |
| C. 规则主体 + 工程触发 + Review 阻断 | 复用现有职责，覆盖设计到交付，可明确 `BLOCK` | 需要同步三个 Skill 和注册表 | 多文件规则需保持一致 | 三个现有 Skill 正好对应记录、执行、验收 | PASS |

### 评审质疑

| 质疑点 | 回应 | 决策依据 | 对决策的影响 |
|---|---|---|---|
| 是否要求每行代码都写理由，造成噪声？ | 以“每个逻辑修改”为记录粒度；机械改动可按共同原因合并，不做逐行流水账。 | 理由必须可追溯，但重复信息会降低审查质量。 | 保留方案 C，增加机械修改合并规则。 |
| 是否应给所有函数无差别加注释？ | 新增或行为变化函数强制函数级 why；简单访问器、生成代码、框架样板可豁免，但必须记录类别和理由。 | 用户要求细化到函数层面，同时注释不能只复述代码。 | 保留强门禁，加入显式豁免而非静默省略。 |
| 只有 Markdown 规则是否算实现？ | 同时接入工程阶段路由和代码评审 `BLOCK` 门禁，并执行注册表、静态断言和独立前向评测。 | AGENTS.md 禁止仅文档声明视为闭环；本任务对象本身是 Skill 规则，因此可执行触发与评测是核心证据。 | 增加流程触发、审查门禁和验证。 |
| 是否需要额外新建 ADR/变更目录？ | 不强制新目录；优先复用项目已有 ADR、任务记录、PR 或 change log 位置。 | 避免违反项目结构规则并减少文档树膨胀。 | 在规则主体中明确复用权威位置。 |

- 决策：采用方案 C。
- 接受的代价：三个文件存在少量重复门禁文字，用于确保不同阶段单独加载时仍不漏检。
- 回滚方式：可分别撤销三个 Skill 的新增段落及 README 生成器映射，不影响其他技能目录。
- 验证：运行 `quick_validate.py`、README 生成器、内容断言、`git diff --check`，并用独立代理按真实工程请求前向评测。

## Change C-001：增强 `documentation-and-adrs`

- 文件与范围：`skills/agent-skills-ao/documentation-and-adrs/SKILL.md`。
- 修改原因：原 Skill 只笼统要求记录 why 和替代方案，缺少质疑记录、逐次修改影响、函数级结构化 why 和缺失时的 `BLOCK`。
- 选择：加入决策链、方案比较表、质疑表、per-change 记录、函数注释模板及验收清单。
- 影响：该 Skill 可独立指导完整理由留痕；新增或行为变化函数有明确注释契约。
- 未触及：不新建项目级 ADR 目录，不强制项目采用某一种文档工具。
- 验证：待统一验证阶段回填。

## Change C-002：接入 `engineering-skill-flow-zh`

- 文件与范围：`skills/engineering/engineering-skill-flow-zh/SKILL.md`。
- 修改原因：规则主体若只在设计或交付阶段加载，Main Build 的逐次修改与函数注释可能漏掉。
- 选择：在 Solution Gate、Main Build、Review、Ship 和自检中分别加入必需产出与阻断条件。
- 影响：复杂工程从候选筛选到交付都必须保留理由链；缺少任一关键部分不能通过 Review。
- 未触及：不改变单阶段一个主 Skill、最多两个辅助 Skill 的预算。
- 验证：待统一验证阶段回填。

## Change C-003：增强 `code-review-and-quality`

- 文件与范围：`skills/agent-skills-ao/code-review-and-quality/SKILL.md`。
- 修改原因：没有独立审查轴时，理由记录容易成为作者自述而非可验证门禁。
- 选择：将五轴评审扩为六轴，新增 Decision Traceability、质疑记录表和 `Request changes / BLOCK` 规则。
- 影响：评审者必须检查候选、依据、质疑、修订影响和函数 why 注释，不能替作者补写理由。
- 未触及：保持原正确性、可读性、架构、安全和性能审查不变。
- 验证：待统一验证阶段回填。

## Change C-004：同步 README 生成源

- 文件与范围：`skills/scripts/Update-SkillsReadme.ps1` 里的中文描述和触发词映射。
- 修改原因：该仓库的 `skills/README.md` 由脚本生成；只改 Skill frontmatter 会被生成器的固定中文映射遮蔽。
- 选择：更新两个受影响 Agent Skill 的中文说明与触发词，再由脚本生成 README。
- 影响：用户可通过“优缺点、评审质疑、修改影响、函数级为什么”等关键词发现正确 Skill。
- 未触及：未改变生成器函数行为和注册表分组，因此无需修改 `Get-RelFromSkillsRoot` 的函数注释。
- 验证：待统一验证阶段回填。
