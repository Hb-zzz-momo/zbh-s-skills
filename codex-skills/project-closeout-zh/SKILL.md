# 项目结束后的沉淀整理

目标是用户能凭目录名找到正确用途、正确版本的文件。文件没丢、链接存在只是安全底线，不等于整理合格；把原来的混乱整体套进新目录属于未完成。

## 定位与边界

- 先核真实项目根、结束范围和落点；当前聊天目录、同名空目录、子项目不自动是同一个目标。活动结束不代表其中的开发项目也结束；仍在编辑/运行的单元留原位，先索引。已有归档先读其README/清单核验现状；没有重整要求时只处理新增材料。用户明确要求纠正旧分类、用途或版本时，对既有材料重新勘验、冻结映射并受控重归位；禁止重复套娃或无依据反复搬动。
- 续做先接上既有主映射、补充映射及导航修订记录，列出现存问题和本轮变化；已归位且无漂移的材料不再重复搬运或再建沉淀副本。仍有子目录的旧分类须核完整成员树，不能因顶层没有文件就叫空目录；读取不全或占位状态不一致时保留未核实边界。
- 使用已安装的 `project-structure-architect` 检查现有结构，并读取该技能的 `references/document-versions.md` 作为共用版本规则；从当前技能目录表定位实际路径，不硬编码用户名或安装盘符。活动档案不套科研/网站脚手架；普通小文档复用 README 即可，已有 manifest 和工程/课程/科研检查仍有效。
- 历史只读恢复沿用已有记忆入口，不初始化新库。复用 `artifact-curator-zh` 的清理能力，不另写删除器；过程经验用已有反思技能接入同一份收尾记录。
- “整理/试用”覆盖任务内可恢复迁移；删除授权按当前指令和已适用授权单独判断。缺授权时先做到可审的精确清单，再问一次最终动作。不要重复索要已有授权。
- WPS/OneDrive 中移动、改名、删除可能同步到云端。只报告本次本地结果；不能声称云端也已完成，或把删同步文件当作仅释放本机缓存。迁移后旧空壳重现、占位状态改变时，保留时间点和客户端实见状态，不反复删除或重建分类；本地整理与本项目云端状态分别验收，全局同步队列不能证明某个项目已同步或未同步。

## 先看内容，再裁定用途与版本

迁移或删除前运行 `scripts/archive_project.py scan --root <受影响项目绝对路径> --out <项目外临时目录>/inventory.json`，完整核对受影响集合；日常新增/更新仅核主题、同用途入口、碰撞及受影响链接，不重做全量收尾。输出目录先确定唯一用途，不覆盖已有报告；迁移扫描包括隐藏文件、工程缓存、压缩包与空目录，不静默排除大目录。读取失败/重解析点明确列出，未覆盖的目录不能当空目录。哈希可能让云端文件下载到本地，空间不足时先报告，不能只扫小文件声称完整。Windows 深层目录报“找不到路径”时先核长路径读取限制，不能当作文件不存在；禁止为绕过失败而隐藏缓存目录、改系统设置或放松链接保护。

1. 读业务原件、修订说明、交付清单和真实内容；文件名、日期、旧README仅是线索。对每个版本族至少核对关键正文/画面/工作表、格式及当前文件指纹，不能只读生成的摘要。
2. 建立“主题—用途—内容版本—当前入口—差别—证据—处置”表。比较的单位是相同用途：上午稿和下午稿、填写模板和排版证书、不同问卷样本/拼车口径、带日期/去日期/刀线/透明底设计，是需要并列的场景，不是简单的新旧关系。
3. 同名PPT/PDF、源码目录/源码ZIP逐项验证对应关系；旧清单审核了另一个哈希、抬头/正文不同、代码有改动时，明确拆版，不能共享“已验收”结论。无法证明实际采用就只说内容和可编辑性，不冒称现场用过或印厂认可。
4. 选定每个主题、用途和文件角色的唯一当前入口。Word源稿、PDF阅读成品与签发凭证可并存，但核实其对应关系。已有明确交付和修订证据就落实选择；同用途冲突列出差异与缺口，不按mtime选新。旧版本进入主题/用途的历史区，保留来源与替代关系。

## 按业务主题组织日常入口

建议落点是项目根下唯一的 `项目沉淀/`，已有等价目录则复用。根据实际内容裁剪主题，例如活动可用“赛事方案与参赛须知、主持稿与活动宣传、获奖证书、贴纸海报与设计素材、志愿者签到与费用、参赛项目源码与试玩、活动照片与复盘”。软件项目应使用自己的产品/模块名，不硬套活动目录。

- 第一层回答“在做什么/找什么”，如“活动宣传”；有内容时才建 `编辑稿/发布快照/历史版本/制作与核对记录`。真实并列受众、场次或规格放 `主题/并列用途/<具体用途>/<角色>/`，例如 `主持稿/并列用途/上午场/编辑稿/主持稿.docx`。优先减少重复层级，真实用途与角色多一层是可解释例外；工程内部结构依依赖保留，不以三层上限机械压平。
- 日常入口不得暴露 `outputs`、`skill-outputs`、技能名、`retype`、哈希或纯日期作为分类。生成器外壳通常混有多个业务主题，须按内容拆开；不能把它整体改名成“历史资料”来规避。
- 编辑稿可持续维护；发布快照冻结有证据确认内部交付、外发或提交的具体版本，文件名带版本标识，更正另留新版本不覆盖。未确认稿按事实标“待确认”留编辑稿，不能伪称已发布或丢进历史。并列用途互不替代。
- 制作脚本、QA、渲染页、before/after、临时检查图进入所服务主题的`制作与核对记录`，不新建 Skill 输出桶，不占据日常成品列表。已有依赖工程/科研输出不强搬，先核最小依赖边界。
- 只对真正有依赖的单位整件保留：Unity/软件工程、可运行包、设计工程的资产依赖。DLL、Resources、Unity `.meta`不拆。一次工具调用的输出目录不等于依赖单位；先辨业务文件和技术记录，再判断最小依赖边界。
- 简化无意义的“副本(2)”“draft/final”名字，用已核实的场次、抬头、样本数量、改动或格式角色命名。文件缺后缀需查文件头再改；扩展名不同不能默认内容同版。
- 原始资料、模板、失败证据、签发/许可和内部协作材料均有明确位置；内部资料标内部使用，不抄个人明细进公共导航。未知文件保留并写明未知什么，不按年龄当垃圾。
- `99_归档记录`只存操作证据，不混入日常素材。已有不可改写的审计记录保留原事实，加旧→新映射和本次更正，不能把上轮安全校验篡改成内容可用性通过。

### 控制文件夹数量

目录不是越细越好，不预建空的主题、用途或角色。新增一层前说明它区分了什么；单文件不为凑模板制造版本表，重复文件名的套娃应合并。确有并列用途、工程依赖、权限边界或旧版隔离时保留必要层级；不能为了层数把源稿、已交付快照和历史混回一起。小主题在已有README写几行当前入口与来源即可。

每轮核对重整前后目录总数，另外分开普通业务目录、真实工程原生目录和操作记录，列出新增/合并原因；不得拿大量工程缓存掩盖业务分类膨胀。先检查单文件套娃、空壳、按日期/工具/每次运行分叉和源稿成品的重复分类；需要合并时保留路径映射并修复当前链接。目录数下降本身也不代表好找，仍要用真实找文件任务验收。

形成冻结的 `plan.json`（格式见[执行与恢复](references/operations.md)）。根README只做简短导航、版本差异和恢复说明，不以几十条链接代替物理归位；正常资料位置应靠名字就能理解。旧导航按本次授权更新，旧版留入本次整理记录；用相对链接避免再造整份副本。

## 版本与占用取舍

1. 按主题建立简短版本说明：用途并列/同用途修订/历史/存在冲突，列内容差别、证据、当前文件和保留理由。不要把“全保留”或写一张版本表当作完成版本整理；物理入口必须同步分开。
2. 同字节副本用 size+SHA256 分组，但仍检查用途、路径依赖、原始截图、证书、失败证据、交付引用与保留者。不得全项目逐文件去重工程依赖，或把同内容许可证删成“多余”。
3. ZIP 与解压目录不能只凭同名推断可互相替代。要清理其中一份，核对全成员、成员内容、隐藏文件、所需权限/格式和恢复入口；CRC 成功不等于与目录一致。巨大的非重复备份列精确审查项，不自动删。
   独立恢复备份不参与工作目录自动去重，备份轮换另按真实授权执行；同一同步树中的副本不能声称独立备份，不为安全再复制整套工作目录。
4. 先迁移并核验保留集合，再按 `artifact-curator-zh/references/experiment-closeout.md` 构建精确清理计划，使用其 `closeout_artifacts.py` dry-run/apply。只有明确授权、消费者停用、保留者与证据通过时执行；受控执行器拒绝云盘重解析路径时保留候选，不能绕过改用递归删除。
5. 迁移同盘不释放空间。分别报告逻辑总大小、同字节重复候选、实际删除字节；没有测量不报物理空间节省。文件占的是磁盘空间，RAM 占用由进程决定。

## 迁移与恢复

- 先查文本引用、启动入口、索引和导入路径。工程/运行包整件迁移；对跨业务混杂的生成器目录按上述内容表拆解。脚本与必要资产保持最小依赖闭包；未验证复现的历史制作脚本明确标记，不冒称能直接重跑。仍在写入的部分先保护，只整理不依赖它的部分。
- 冻结 `inventory.json` 与 `plan.json`，同一轮独立评价时不修改输入。预检源成员/指纹、目标碰撞、路径越界、嵌套移动与链接，并检查含根目录的完整路径及 Windows UTF-16 长度。`>=240` 只是保守提示阈值，不是 WPS 官方限制；通过预检不证明 WPS 能打开或云同步完成。消费者由执行者实际检查，计划里的布尔字段不是授权或检测证据。
- `apply` 逐件同卷重命名，不复制整份归档；执行前记录 intent，之后记录 done。失败保留 partial 日志，按日志核对实际状态后恢复，不盲重试。跨卷不支持该执行器，应另做经核验的复制迁移方案。
- 迁移后生成每个原文件的旧→新路径映射。更新当前导航和仍生效的可修改入口，包含归档外的项目根README及已知外部索引；历史证据不改写。无法修复的历史绝对路径列为已知限制，提供映射查询，不能声称旧路径都能直接打开。
- 用 `verify --plan` 对计划覆盖的冻结文件逐一回读哈希，检查 `files_outside_plan`；未移动项另按原清单核验，不能把部分覆盖说成全部原件通过。另检查新增导航的链接、空目录、真实源码/成品入口。哈希只证明内容完整，不证明程序已运行、排版合格、活动结果或平台提交。
- `rollback --journal ... --out ...` 可反向恢复迁移；新增导航/报告不自动删除。恢复后再校验原位数据。命令与限制见[执行与恢复](references/operations.md)。

## 验收与交付

按 `multi-agent-evaluation-zh` 安排独立评审；涉及大量真实迁移/删除、复杂依赖时追加独立复核。评审者只读冻结的技能、原清单、迁移映射和真实产物，可在隔离临时目录做行为测试，不复制整个项目。保留原始意见、真实代理身份、输入哈希及修订复验。

安全验收：范围正确；全部原文件有处置和回读依据；无覆盖/丢失；依赖单元未拆；失败/回滚实测；重复候选与实际删除分开；敏感资料未公开。

内容可用性另验，不能用前述安全通过代替：安排未参与目录设计的真实评审者，只给实际目录树和5—8个找文件任务，首轮不读README、计划或作者给出的目标路径。任务须覆盖新增文件落点、继续编辑的源稿、已确认冻结版本、两种易混淆的历史/当前版本、并列用途避免误用、内部资料与复盘，可组合为同一任务。记录首次选择、实际路径、所经层数、是否误入制作记录、内容是否选对。找错用途/版本、必须翻README才知放哪、日常文件仍埋在生成器桶里，均为阻断；先修复再复验。工程内部约定不因目录层数而被扁平化。

还要核版本表与实物内容一致、不同格式确实同版或已明确拆版、有来源的复盘和下次动作可找到、当前导航与历史记录区分。目录增减与原因必须可解释，不用多造文件夹或多写说明代替整理。复盘指出本轮是否因工具桶、分类过细或检查产物增生让目录更乱，并落实合并或保留理由。未验证内容列边界；未解决的可用性阻断不能凭文件数/哈希、自评或旧评分覆盖。

链接核验从实际项目入口开始，不能只检查归档子目录。验收链接须指向标明批次的真实结果，主映射与补充映射一起给出；历史同步队列、统计和“尚在同步”等描述带观测日期，未经本轮重验不写成当前事实。续做结果另记本轮范围，不改写历史通过/未通过，也不把旧全量校验当作本轮全部文件又检查了一次。

最终直接说明整理入口、前后文件数量/逻辑大小、实际删除及保留版本、真实试用和独立评价结果、未验证项。给一句以后可直接说的调用语。技能制作/单测/一次试用分别报告，不能保证未来自动触发或长期效果。

设计来源与未采用方案见[来源与取舍](references/sources.md)，只在设计或维护时读取。
