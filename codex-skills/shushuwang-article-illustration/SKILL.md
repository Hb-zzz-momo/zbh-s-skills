# 炒技鼠鼠王：文章与模块配图

适用于用户的“炒技鼠鼠王”自媒体内容与 `E:/project/自媒体` 项目。以下是本用户的内容偏好，不推广到其他用户或无关项目。当前明确要求优先；用户只要求更新 skill 时，仅更新规则，不顺带生图、改稿或发布。

## 优化任务：先研究，再全平台落地

用户说“排版不好看”“更容易读”“优化一下”“别的平台为什么没改”时，按这个顺序做，不许直接改一版交差：

1. **先找参照**：读 2–5 篇同题材、同平台的高质量样本（能读到互动量的就记下来），记下可迁移的机制——标题怎么写、开头给什么、段落多长、图注落在哪、用了表还是图，来源和数字写进编辑记录。样本清单与排版参数见 [references/readability-and-traffic.md](references/readability-and-traffic.md)；文风样本见 [references/voice-and-reading.md](references/voice-and-reading.md)。没有新样本时复用已有调研，不为小修反复检索。
2. **先量再改**：改之前量一次（最长自然段、图数、表数、加粗数、字符数），改完再量一次，前后数据写进自检记录。凭感觉说“更清爽了”不算通过。
3. **一平台 → 全平台**：任何在一个平台生效的改进，必须在同一轮落到所有会发布的平台，逐平台核对图注落位、分隔线、表格、引用块、字号层级。只改一个平台等于没改，这是用户明确要求过的。
4. **平台内验收**：本地渲染通过不算通过。能在编辑器里打开的（知乎、雪球）就打开核对 DOM；打不开的（公众号后台被浏览器策略封锁）写清“待用户在编辑器确认”，不能写成已完成。
5. **失败也要沉淀**：被平台丢掉的样式（雪球丢表格、列表、缩进、分隔线；知乎丢首段缩进）写回本技能，下一次不再重踩。

## 自检之后必须迭代（自检 → 改 → 复查 → 加断言）

自检不是交付前的仪式，而是下一轮的输入。这轮基金课的经验：每一次用户说“不行”，都说明**验收维度缺失**，不是审美玄学。按这个循环走：

1. **写成现象 + 证据**：哪个文件、哪张图、哪个平台，实测数字是多少（例：雪球 `tables=0`、卡片手机等效字号 4.7px、图注字段为空）。不写“感觉更清爽”。
2. **改根因，不打补丁**：一个平台的毛病先判断是不是共性——图注在知乎丢，其它平台也会丢，就统一改图注落位；字号在手机上看不清，就是所有卡片都要按手机等效字号重做。
3. **把坑变成断言**：每修好一类问题，就在脚本里加一条检查，让下一课自动挡住。这轮新加的：表格→图、图注→平台字段/图下行、公式→引用框、卡里公式→`<sub>`、卡片字号→手机等效、标签→不压图形。
4. **重跑全部检查**：不只跑改动项；数字、三平台稿件、公众号 HTML、两种宽度渲染、图片自检全部重跑，任何一项失败都不交付。
5. **记录本轮**：问题 → 改法 → 复查证据 → 新增断言，写进该篇 `编辑记录/自检.md`。
6. **到限就停**：同一维度最多迭代 2–3 轮；仍不达标就写明限制与原因（例如“公众号后台被策略封锁，最终排版待用户确认”），不无限打磨，也不把未验证项写成已通过。

## 发布前必须依次过两道 humanizer（2026-09-26 用户硬要求）

用户明确规定：**以后所有 AI 生成的自媒体文章，发布前必须用 `humanizer-zh` 和 `zh-humanizer-literary` 修饰优化，缺一不可。**两者定位不同，顺序不能反。

**第一道：`humanizer-zh`**（去 AI 味 + 事实锁）

- 以**嵌入模式**调用：只返回终稿，不输出分析、草稿或自我评价。
- 先建立事实锁：人名、机构、产品名、数字、日期、引文、链接、因果、否定词、范围词、不确定性。
- 按 `references/chinese-ai-patterns.md` 的四组检查：内容层、语言层、结构与节奏、平台模板腔。
- **只处理成簇出现的痕迹**：单独一个"此外"、一个破折号、一句排比不算 AI 味，别乱改。
- 改写后逐项复核事实锁；终稿新增的事实、数字、引文、动机一律撤回。

**第二道：`zh-humanizer-literary`**（编辑判断 + 文采）

- 区分两类债：**内容债**（缺事实、无真实例子、无观点、受众不清）与**语言债**（套话、结构过齐、连接词过多、升华式结尾）。
- 用真实场景、证据、取舍、动作替换空泛表达；只在有助于记忆的地方提升语言；结尾落在下一步、未解问题或具体后果上。
- 质量检查用该 skill 自己的清单（读者是否知道为什么现在重要、最强句子去掉形容词是否成立、有没有一个能被记住的短句）。
- 不许编造资历、案例、数字或结果；不许把 AI 味换成鸡汤味。

**顺序不能反**：先净化再提升。反过来会把第二道加的文采当 AI 味删掉。

**两道都改完之后**：重跑内容门禁（数字、事实、品牌）→ 正文有改动就四个平台全部重推。`自检.md` 里要写清"这两道各改了什么、为什么"。

**别叠第三个 humanizer —— 会叠出"Humanizer 味"。**

- 把多个 humanizer 串起来跑，会把所有不规则表达一起磨平，从"ChatGPT 腔"变成另一种统一的"假人类腔"。
- 两道就是上限：`humanizer-zh` 净化，`zh-humanizer-literary` 做编辑判断。再想提升靠**你自己的文风基线**，不靠第三个工具。
- 上面写的"顺序不能反"是**推理结论，没有做过对照实验**。若某篇改完反而更平，允许只跑第一道，并把结果写进自检。

**最终校准用 [references/my-voice.md](references/my-voice.md)。**

- 那是从**用户自己已发布的稿子**里量出来的基线：零破折号、零感叹号、零中文括号、极低第一人称（0.4–1.8‰）、40–60 字段落、20–30 字句。
- **优先级高于任何通用 humanizer 的建议**。冲突时以它为准——例如"多加『我』来做人味"在实测样本里是错的。
- 每积累 3–5 篇已发布稿，重跑 `_voice_profile.py` 刷新它。

**工具链选型也要先研究。**

- 这一节本身就是教训：2026-09-26 用户点名两个 skill，我直接装了这两个，没有扫这个品类的其他方案（当时检索结果里已经有 10 个同类仓库，我一个都没看）、没有比较、也没提出"该不该叠"。用户拿 ChatGPT 的调研结果来对比，差距是真实的。
- 规则：**收到"用某个工具"这类指令时，先做一次检索确认这个品类现在的选项和取舍，再动手**；发现更合适的组合，先讲清楚再执行。内容要研究，工具同样要研究。

## 文章先行

### 不变层 / 可变层：模板只固定底层（2026-09-26 用户定调）

用户的原话："如果模板太一致不太行，教学是可以的，但技术分享、信息分享这些，除了底层字体、命令框、表格、引用框格式固定，其他内容格式还是灵活一点好看。"判断依据是同账号那篇《Harness 为什么开始少用向量数据库了？》——它"有逻辑同时不死板"。

**不变层（跨文章统一，这才是"底层"）**

| 固定什么 | 取值 |
| --- | --- |
| 正文字号 / 行高 / 段距 | 17px / 1.85 / 15px（公众号；其它平台用平台默认） |
| 小标题 | 23px、`#184c50`、带「N. 」序号、上 36 下 18 |
| 图片 | 通栏、无圆角、`margin:24px auto 10px` |
| 图注 | 两级：图题 15px 加粗 `#506665`；来源 14px `#60706f`、`margin:8px 0 24px` |
| 代码 | 行内 `0.94em` + 浅底 `#edf3f2`；代码块深底 `#172d33`、圆角 8、padding 14/16 |
| 表格 | 表头浅底 + 只留横线，三列 26/24/50 |
| 引用 / 结论框 | 左 3px `#29908e` + 浅底 `#F3FAF8`，16px/1.85 |

**可变层（每篇按题材重新决定，不要从上一篇复制）**

- 用几张图、图放在哪几节、每节是否配图；
- 图的形态：真实截图 / 原始图表 / 自制机制图 / 表格图 / 代码图；
- 重点靠什么承担：行内加粗，还是底色框；
- 来源放哪：脚注编号 + 文末"资料与图片来源"一节，还是每图一张来源卡；
- 小节长度与节奏：允许有的节很长、有的节只有两句。

**按题材分流**

| 题材 | 结构 | 配图策略 | 重点怎么给 |
| --- | --- | --- | --- |
| 课程 / 教学 | 小节等长、节奏均匀，可套统一小节模板 | 机制图 + 表格 + 公式卡 + 自测卡，卡片可以多用；文末必带逻辑链路卡 | 结论、公式进框 |
| 技术分享 | 正文为主，节与节长度不均 | **真实证据图为主**（别人的原始截图、官方页面、真实数据），自制图只在真要解释机制时用；不要求每节配图 | 行内加粗，少用底色框；来源用脚注 + 文末来源节 |
| 信息分享 / 观点 | 正文 + 少量证据图 | 同上 | 同上 |

**反模式（做完自查，命中就重做）**

1. 每节都套同一张卡，像幻灯片；一篇文章里出现"同一组卡片全家桶"。
2. 每篇都是同一组图：机制图 + 案例卡 + 公式卡 + 自测卡 + 链路卡。
3. 用底色框承担本该由行内加粗承担的强调（同账号那篇全文 0 个底色框、24 处加粗）。
4. 每张图都做一张"来源卡"，而不是脚注 + 文末来源节。
5. 图比说明多：图成了主体，读者在猜图要说什么。

### 颜色要分轻重，内容要有详略（2026-09-26 用户补充）

用户原话："那篇技术文章颜色有轻有重，内容详略得当。"这句可以量化。按"每种颜色承载了多少文字"统计，同账号那篇和我们的模板稿差别是：

| 层次 | 用在哪 | 颜色 | 那篇实测占比 | 我们的稿子 |
| --- | --- | --- | --- | --- |
| 重 | 正文 | `#333` | 72.5% | 83.7% |
| 重 | 小标题、关键判断 | `#184c50` | 3.6% | 5.3% |
| **轻** | 图注、来源、说明、次要素 | `#506665` / `#60706f` | **15.9%** | **5.1%** |
| 底纹（浅） | 结论 / 引用框 | `#F3FAF8` + 左 3px `#29908e` | 6.7% | 6.7% |
| 底纹（深） | 代码块 | `#172d33` 底 + `#e8f6f3` 字 | 4.6% | 0 |

两条硬规矩：

1. **次级文字要占到 10% 以上。**低于这个数就说明整篇都是"重"的，读者没有轻重对比——我们的模板稿只有 5.1%，那篇是 15.9%。次级信息指：图注、来源、边界说明、"注意这里不是 X"这类澄清、脚注、文末来源清单。
2. **底纹至少要有两个层次。**只有一种同色浅底（我们现在就是）会显得平；有代码/命令的题材要给深底块，让"技术细节"有自己的视觉重量。

配套工具：`assets/check-color-weight.py`，传入公众号稿直接打印这份占比表，次级低于 10% 会告警。

**详略还有一层**：别把每段都写成同一个粒度。给读者留"可以跳过"的部分（来源、边界、延伸阅读），它们同时也是颜色上的轻层。顺带一条实测结论——**节长度要不要均匀并不是关键**：那篇 6 节里最长/最短约 1.6 倍，我们那篇 4.8 倍，反而更不均；真正的差距在颜色层次和次级信息比重。

- 默认交付可独立阅读的文章。以连贯文字讲清问题、实际经历、步骤和结果，代码与表格按内容需要保留。
- 先写文章、确定模块，再判断哪里值得配图。不要把正文变成大字海报、知识卡片串或密集信息图；发布到小红书也不能仅因平台名称就自动改成图卡。
- 图片承担具体作用：解释一个难点、展示必要信息，或在长段技术内容间提供轻松气氛。说不清用途的图不生成，不要求每个模块配一张，也不预设固定数量。
- 用户强调配图要有信息量，优先解释只靠文字难以说清的路径、边界、层次和差异。“克制”不等于图越少越好：先找读者难点，再决定需要几张。只有角色表情或泛泛类比的图不能代替机制解释图。
- 解释图需让读者看清对象、关系、方向或前后差异；Logo 角色只辅助提示，不占据主要信息空间。按手机实际显示宽度核对标注，信息图不能沿用装饰插画的小尺寸而使文字不可读。
- 配图靠近相关段落，控制展示尺寸与留白，让正文保持主导。平台强制要求封面时，单独处理封面，不用封面式设计替代正文配图。

## 每篇**课程**文末要有「本课逻辑链路」卡（2026-09-26 用户要求；技术分享类可选）

所有课程文章的最后一节，放一张把本课逻辑串起来的链路图，走位照用户手绘的样子：上排从左到右，在最右端掉头，第二排从右往左，需要第三排再掉头。目的是让读者读完整篇之后，用一张图把骨架收回去。

**适用范围**：课程 / 教学类必做。技术分享、信息分享类**不强制**，只在文章本身就是在解释一条链路时才用——那种题材里模板化反而显得死板。

- **位置**：正文最后一个 `##` 小节，标题「一张图看懂本课逻辑链路」，下面一行短句（≤20 字）+ 这张图；免责声明排在这之后。
- **形状**：4 列 2 行最省竖直空间（实测 1080×484）。一步一格，格内只放 3–6 个字的短语，不写整句。
- **箭头**：上排用 `→`，掉头处一个垂直 `↓`，下排用 `←`；下排那三个/四个格子要 `justify-content:flex-end` 右对齐，掉头的竖箭头才对得上同列。
- **文案**：每行最多 6 个全角字，换行处手写 `<br>`，不要让它自动断成「基金买底层资 / 产」。
- **标题**：卡内只留「本课逻辑链路」，不加副标题，省下的高度给格子。
- **模板**：`assets/figures-card-template.html` 里第 5 块 `#fig-chain` 连同 CSS 直接复制。
- **落地范围**：一次改动要落到本系列**所有**已发课程，不能只改当前这篇。

## 公众号正文必须自带排版参数（2026-09-26 定稿）

## 易读性与引流：默认执行

用户要求文章"易于阅读、易于接受"时不再逐篇重复交代：短段落、重点加粗、比较表、流程图、命令/公式框是默认工具箱，网络图片按需引用。完整规范、调研样本与出处见 [references/readability-and-traffic.md](references/readability-and-traffic.md)。

- 长段在 60–80 字断开，一段只说一件事；加粗只给判断、易错点和关键数字。
- 每个大部分至少一个可视化抓手：比较表、机制图、流程图或命令框，按"读者在哪一步会卡住"选，不默认全上。
- 命令、代码、公式、文字版流程在公众号必须用 section 底色框；`<pre>` 的底色会被编辑器丢掉。
- 标题写"读者得到什么"，系列用固定前缀；开头一两段交代读什么、给谁读、怎么读。
- 图片优先级：自制机制图 > 官方/权威来源的网络图 > 装饰插画。引用网络图片要打开原页面核对，并在图注写明来源与日期；找不到合适且可引用的图就不放，不用无关库存图充数。
- 引流靠结构、钩子和首发平台契合度，不靠标题党、虚构亲历、诱导分享；金融等合规敏感题材不点具体产品、不承诺收益。
- 成稿前按 references 里的验收清单逐条核对，含手机宽度预览；平台格式差异（公众号无超链接、雪球 AI 标识等）分别处理。
- 机制图、对比表、公式卡、自测卡的可复用骨架在 [assets/figures-card-template.html](assets/figures-card-template.html)，渲染与自检脚本模板是 [assets/figure-render.cjs](assets/figure-render.cjs) 和 [assets/figure-check.cjs](assets/figure-check.cjs)：整目录复制到该篇 `编辑记录/` 再改文字与断言；图内只放内容，“图 N｜标题”交给平台注释字段或图下小字。
- **图要按手机验收**：等效字号 = 图内字号 ×（375 ÷ 卡片宽度），关键文字 ≥12px、说明小字 ≥9px；画布建议 1080px 宽、正文 28–30px。还要查内容溢出、标签压图形、柱状图数值与标注是否一致、**图片（logo、贴图）有没有压住文字**（脚本 `check_figures.cjs`，模板见 assets）。压字检查要用 `Range.getClientRects()` 取真正着墨的文本框——块级元素占满整行，直接比 `getBoundingClientRect()` 会误报。**封面单独看**：主标题最多两行，超过 12 个全角字就拆成「眉题 + 两行主标题」，logo 与副标题、署名互不重叠；封面标题排成三行、末行只剩两三个字，一律算不合格。脚本查不出“看着别扭”，渲染后仍要自己看一遍。
- **文字必须待在它自己的框里**：任何有边框或底色的元素（封面侧栏、公式框、表格格、链路格）都要逐格验——用 `Range.getClientRects()` 量出的着墨框不得越出该元素边界。封面右侧「底层资产（股票 / 债券 / 黄金）」就是这么溢出 20px 的，只查卡片总溢出根本发现不了。**越界同样算失败**：卡片是 `overflow:hidden`，绝对定位元素越出卡片会被悄悄裁掉，也要报错。
- **贴图不得盖住边框线**：logo 默认是透明底 PNG，但一旦给它写了 `background`/`padding`，那个不透明方块就会把后面的相框、表格线、分割线**盖断**（用户 2026-09-26 连续两次指出）。两条硬规矩：① 封面 logo 不写 `background`/`padding`，并收进相框内侧留出余量；② 图注里的 logo 用 `flex` 排在注释右侧，不要绝对定位。检查时**只比边框那四条带**（`getBoundingClientRect` 加上各边 `borderWidth` 切出来的带），不能拿元素整块矩形去比——相框内部是空的，比整块会误报。
- **修的时候改结构，不要挪坐标**：logo 从“绝对定位贴右下角”改成“放进图注行的 flex 右侧”，从布局上就不可能压字；只调 `bottom` 的像素值，下次换个文案又会撞上。同理，封面长标签改成「主标签 + 小号副行」，比硬压字号更稳。
- **自检要往“整体最优”走**：每发现一类漏检，就补一条能覆盖同类问题的通用断言（几何包含、跨元素重叠、越界），而不是只补齐这一张图。断言列表见 `references/readability-and-traffic.md` 的迭代实录。
- **公式必须进框，且卡里必须真排版**：正文里的公式不得裸露成普通段落——公众号用 section 框、知乎用 `>` 引用块、雪球/东财靠公式卡图片承载；卡片图里的公式要用 `<sub>`/`<sup>` 排下标上标，禁止写成 `R_A`、`ρ_AB`、`σ_p²` 这类下划线形式。渲染后必须肉眼看一遍公式卡（脚本断言只能证明文字在，证明不了会不会渲染成方框或没下标）。

## 文章文风

### 写出本账号的声音

用户希望文章有自己的风格，情绪有变化，能吸引人继续读。以技术学习者向同学分享的口吻为基调：讲得明白，有具体判断，轻松但不故作热闹。允许困惑、犹豫、意外和自嘲；它们应来自有依据的经历或作者已表达的感受。不要把账号名变成每段必出现的“鼠鼠”自称、角色表演或固定口头禅。

个人风格首先体现为关注什么、如何判断、为什么取舍。保留用户有辨识度的说法和态度，不把句子全部磨成中性说明。尚未确认的口吻只是本篇尝试；不能把助手自己写出的句子当成用户已认可的长期范文。后续按用户具体反馈调整，不靠堆规则把声音写死。

### 先读，再决定怎么改

用户要求参考公众号、知乎等好文章，或明确指出“AI 味重、情绪平、没有吸引力”时，先实际阅读与题材、读者接近的文章，再动笔。已有本次阅读材料足够时直接复用，不为小修反复检索。阅读方法与本次样例见 [references/voice-and-reading.md](references/voice-and-reading.md)。

记录值得借鉴的具体段落机制：开头给了读者什么疑问、解释在什么时候出现、哪次选择改变了进展、幽默依赖什么细节。不要只列链接或概括为“有故事感”。能看到互动量才称高赞，并区分索引数据与实时数据；读的是作者站或转载时如实说明。热度不是事实正确性的证明。

学习推进问题、解释难点和调节节奏的方法，不复制独特表达、私人经历或人设。选择适合本篇的写法，不能每篇套“遇到故障—反复失败—终于成功”。知识解释、经验复盘和观点文章可以有不同的结构。

### 开头先交代本文，再让读者选择阅读路径

这是本账号今后技术长文与跟练教程的默认要求，不仅适用于当前 VPS 文章；执行时无需用户逐篇重复提醒。

技术长文和带跟练步骤的文章，标题后先用简短导读说明本文解决什么问题、覆盖哪些内容、采用什么总体方法，让读者在进入个人经历前知道能学到什么。通常一两小段即可；不写成论文摘要，不堆术语，不用“干货满满”替代具体内容，不抢先重复全部细节。

提供可点击的阅读目录，优先区分“从头了解过程”和“直接操作跟练”，按内容需要加结果或参考资料入口。跟练部分较长时，在其开头提供步骤目录。跳转到跟练应先看到适用条件和准备事项，不能直接跳过必要前提让读者复制命令。较长部分可提供返回目录链接。

目录使用清楚的读者用语，目标锚点稳定且与正文实际位置一致。检查点击后的落点与手机阅读效果；平台若不保留页内锚点，改用它支持的原生目录，或保留清楚的章节导航。不能把本地 HTML 能跳转当成公众号、知乎等平台已验证支持。短文无需强塞目录。导读负责说明全貌，故事负责展开具体经历，两者都要避免重复。

### 标题层级必须在结构和视觉上同时清楚

长文先按内容关系分成大部分，再划分小节；需要细分的操作才放到下一级。文章标题仅一个一级标题，大部分用二级、小节用三级、具体步骤按需要用四级，不把所有段落标题放在同一级，也不跳级。编号与所属章节对应，目录沿用正文的层级与命名；不要把不同层级混编为连续字母或同一种编号。

排版通过字号、字重、段前留白以及克制的分隔线区分层级，大标题明显大于小节，小节大于步骤。不能只改 Markdown 标记却让显示尺寸近似，也不能只放大字体而保留错误的文档结构。检查手机与桌面的真实显示；若调整标题或编号，同步修改目录、正文中的步骤引用和跳转目标。具体层数按文章需要确定，不为了统一模板强塞四级标题。

### 让内容带动情绪和节奏

- 不把文章写成连续的“我做了 A、我又做了 B”。关键处交代当时依据什么判断、结果与预期哪里不同、下一步为什么这样选。“我”的数量不是文风指标；删掉主语并不能解决流水账。
- 用具体变化承载情绪。服务运行却连不上、两项检查给出不同结果、一个办法解决了旧问题又暴露新问题，都能让读者产生反应。不要用“太崩溃了”“先别庆祝”“终于搞定”代替过程，也不要求每段都有情绪或反转。
- 解释跟随读者眼下的疑问，背景够用就停。必要信息可以提前给出，不为悬念故意藏答案、绕路或制造不存在的失败。开头抓住真实问题，不先铺一整套基础课程。
- 段落长短与语速随内容变化：关键发现可以短，机制解释可以展开，连续操作可以列表。避免每节固定概念、步骤、总结，也避免把所有句子拆成刻意停顿的一行。
- 幽默落在具体处，少量即可。删除笑话后仍应有内容推进；不能靠网络热词、感叹号和密集反问假装亲近。结尾停在实际结果、仍未解决的问题或读者下一步，不强行升华或重复全文。

需要改文风时使用可用的 humanizer 技能辅助清理套话、重复结论、强行升华、机械的“不是……而是……”和每节相同的总结句。它负责辅助检查，不能替代对作者声音、具体细节和阅读节奏的判断。

不为自然口吻编造亲身操作、心理活动或测试结果。改文风应保留代码、命令、数值、来源以及实际验证范围；不能为去掉“AI 味”损失手把手教学所需信息。

以从未接触过技术的同学为默认读者：术语首次出现先解释用途，必要时给一个不过度延伸的类比；操作写清在哪台设备、哪个窗口执行、哪些值要替换、成功时看什么、失败后查哪里。精炼优先删重复和套话，不删这些必要解释。长配置可放到文后，正文先帮助读者理解过程。

标题优先抓住文章中真实的困惑或具体结果，让读者第一眼知道与自己有什么关系；保留可识别的主题词，避免堆术语、夸大成果和“零基础秒懂、永久稳定”等承诺。

成稿正文不夹入写给用户或编辑的过程说明，如“已脱敏”“以下为优化稿”“AI 辅助排版”等。编辑记录和自检结果单独保存；事实来源与必要限制继续保留。平台自身要求的内容标识如实处理，不把去文风痕迹理解成伪造创作来源。

## 检查与交付

解释性配图必须带读者能直接看到的短标题和必要说明：图片下方独立写“图 N｜这张图解释的问题”，再用一两句交代关键含义、边界或省略条件。Markdown 的 `![描述](地址)` 是替代文本，不能代替可见图注；上传平台后替代文本可能被换成文件名。Markdown 发布稿使用独立加粗段落，HTML 使用可见图注并区分标题和说明的字重。已有图注只更新一次，避免重复；图注不是章节标题，不打乱目录层级。修改或重新上传图片后，在平台预览逐图确认标题、说明、对应图片与相邻正文均正确，保留用户已经上传成功的图片链接，不能只核对本地 HTML。封面和纯装饰性 Logo 按用途决定是否需要图注。

用户明确要求内容、配图和格式严格自检。每次成稿或实质修改后先完成下面三项，再交付或发布；不能把“图片加载成功、无横向溢出、配置语法通过”合称为全文正确。

- **内容核对**：逐段区分实测事实、解释、类比与未验证结论。数值回到原始记录重算，技术结论与配置字段核对官方资料及实际版本；逐项确认前置条件、执行设备、步骤顺序、替换值和验证范围。重排章节后全文搜索旧编号与旧标题，不能只改目录。
- **配图语义核对**：逐图阅读全部文字，沿每根箭头追踪对象、目标、方向、边界和状态，并与正文及真实配置对照。重复标注必须能分清“同一对象重复说明”与“不同对象”；例如两道防火墙放行同一目标端口，不能画得像两个服务入口。不要把正常与失败状态混在一条未解释的路径里。类比及省略的前提需说明，图注不能替一张明显误导的图兜底。最后用零基础读者视角问：脱离作者解释，最容易看错什么？有歧义就改图。
- **格式与跳转核对**：检查从标题到末尾的完整渲染、标题实际层级与字号、目录落点、正文交叉引用、代码换行、图中文字在手机尺寸下的可读性及平台转换后的保留情况。修正后同步所有正式版本，并核对交付文件确实引用新图。

自检记录写明发现的问题、修复内容、核验依据和仍未验证的范围。自动检查和逐项阅读承担不同职责；没有实际完成的检查不能标为通过。发现关键错误或歧义时先修正再继续已授权发布，不需为例行修正重复索要批准；平台登录或验证仍按实际情况处理。

技术长文交付前，确认开头已交代内容与总体方法，目录能区分完整阅读和直接跟练，所有目录链接落点正确，配图确实解释了对应难点；同时核对手机阅读效果。对尚未完成的平台内检查如实标注。

先连读正文，判断读者是否知道为什么继续看、关键转折是否有事实支撑、作者的判断是否具体、笑点是否勉强、解释是否打断当前问题。若仍像操作流水账，重排信息或补回已有材料中的选择与结果，不能仅替换词语、减少“我”或增加情绪词。格式检查通过不等于文风已被用户认可，也不承诺“消除 AI 味”或通过某种检测。

交付前做全文与格式自检，覆盖标题、摘要、开头、所有正文模块、命令、配图图注、链接和文章最末尾，不能只抽查首屏。检查术语是否解释、前置条件是否缺失、命令位置与替换项是否明确、事实和数字是否一致、步骤有无断档、正文有无编辑残留。检查标题层级、段落密度、列表、代码换行、表格窄屏可读性、图文对应和末尾排版；本地预览与平台内实际排版分别核验。自检报告写在独立记录里，不附到面向读者的正文。

把图片放进文章后检查：读者能否靠正文读懂；每张图是否对应附近内容；缩小到实际展示尺寸后是否仍清楚；是否保持原 Logo 身份；有无海报感、装饰堆砌或技术误导。若图片占据阅读主导，先减少数量、尺寸或画面内容，不继续增加修饰。

当用户要求优化已有成稿，先辨认不满意的具体特征，针对性修改。不要只换配色后重新输出同类图。

发布时使用对应平台技能，遵循本次授权范围。已有草稿先更新和检查，避免为了换图重建重复草稿。分别报告本地完成、草稿保存、公开发布状态；不能把旧草稿说成已更新。

平台转换后必须重新验收：同步成功不代表配图已转存，外链图片能暂时显示也不能忽略“转存失败”；代码不得被压平成普通段落，失效页内链接应改为平台原生目录或清楚的章节导航。自动排版可能把解释图缩到当前页剩余空间，须逐图查看最终尺寸，必要时调整图文顺序；不能只检查原图分辨率。长文入口若生成分页图片，应保留文章阅读结构，不套无关库存封面；精简内容时明确文章覆盖范围，不把复盘版称为完整跟练教程。

点击发布后重新打开结果页并检查后台状态，分别记录“提交成功”“审核中”“公开可访问”。成功提示后若链接不存在、跳回首页或加载失败，应记录现场结果及未确认原因，不自动重复投稿，也不能继续宣称公开发布已完成。
