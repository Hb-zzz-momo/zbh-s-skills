# 经验与流程联合沉淀

用于一次反思同时处理经验与工作流程。两侧都检查，但只改有价值且有依据的内容。用户明确只处理一侧时从其范围；另一侧标本次不处理。没有新发现时保持不变。

## 先找已有 Skill 和所有者

先看本次实际调用过的领域 Skill，再在宿主已安装技能目录按能力和触发条件检索通用/专用 Skill，必要时读其相关引用。用户指定目标优先，但必须核对内容、所有者和当前版本；不能只凭同名判定适用。`workflow_index`、项目 runbook 只提供定位线索；缺索引或无命中不能直接判定没有 Skill。多个冲突版本无法裁定时保留分歧。

同目标、同前提已有 Skill 时增量修订，不生成同义“优化版”。跨项目稳定机制归通用 Skill，领域/工具专有限制归专用 Skill；专用层引用通用层，不双份维护相同规则。只有通用层缺陷才改父层；特定项目参数不能固化到通用正文。已有独立流程文档保留历史/案例或项目契约，默认不再作为可复用方法的平行权威。

## 无匹配 Skill 时创建通用 Skill

先记录检索范围和未命中依据，再将实际可复用流程交当前可用的 skill-creator 创建在宿主可发现的用户技能目录；无需用户另行说“创建 Skill”。保持名称/description可发现，入口给出输入参数、适用/排除条件、必要步骤、异常分支和验收；按需链接引用资料。不能只新建项目 runbook 或一个不可执行的空壳。

当前项目作为案例：保留目标、环境/版本、实际步骤、证据、失败/恢复及未验证项，并关联新 Skill 的版本/章节。案例用于说明方法，不把项目路径、账号、固定业务值或一次恢复结论变成通用要求。一次案例只支持限定条件的初始方法，不能冒称普遍有效；只有零散未知片段不足以形成流程时记录缺口，不能伪造步骤。

案例可在 Skill 的引用资料中按需读取；含私人信息的实际案例留原项目/经验库，由私有索引关联 Skill。公共 Skill 只带经过核查可公开的脱敏案例；不将私有案例、受限来源路径或配置随 Git 上传。反向关系可由私有案例索引保存，不能为了双向链接泄露资料。

## 从同一事实得到两类产物

1. 先还原实际执行：步骤、输入/输出、跳转、重复、恢复、验证及未发生部分。实际执行与拟议顺序分区，不能把建议倒填为历史。
2. 经验保留“为什么、依据、适用/不适用条件”；成功、失败、未知均按证据记录。没有新经验也可以因旧经验未接入而修改流程。
3. 流程变更可为补前置条件、调顺序、合并重复、增加异常分支、移除已被证据否定的步骤或把稳定检查交给已有工具。说明变化如何减少问题；流程检查不是每次都加一步。
4. 已有规则被忽略时，先查它是否被加载、能否检索、是否在正确动作前触发，或是否缺执行证据。规则已有且充分时修入口/调用位置，不再复制规则。
5. 一次成功可形成限定范围的暂定流程；普遍化需另有证据。暂时绕路不得静默替换原强制步骤或降低原验收要求。

## 最小关联与变更记录

Skill 使用其名称、权威路径、版本或内容 hash 和稳定章节/步骤定位；不强迫给所有已有 Skill 加 WF 编号或改写结构。已有 WF 编号和旧文档链接继续保留，映射到 Skill/案例。调顺序不重编号；拆分/移除保留旧定位到新定位的映射。

经验可选的 `workflow_links` 沿用旧字段，也可指向 Skill 名称、路径、修订版/hash、章节/步骤及关系。Skill 引用可公开的经验/案例；私有关系按上节用私有索引维护。一个关联处记录一次理由，不复制整张卡。

修订最少写：

| 字段 | 含义 |
| --- | --- |
| workflow_id / target | Skill 名称/原有流程 ID，以及实际修改文件；专用→通用依赖 |
| base_revision / base_hash | 修改前读到的版本，写前重读核对 |
| step_ids | 修改影响的稳定步骤 |
| evidence_ids | 支持、反例和建议的来源；无证据说明缺口 |
| before → after / rationale | 最小可审核的内容差异及理由 |
| acceptance / rollback | 如何检验改变、哪些结果要求撤回或修订 |
| application | `unchanged` / `proposed` / `applied` / `partial` |
| verification | 实际做过的检查及范围；未执行就写未验证 |

`applied` 只表示目标文档已按预期写入，不表示新流程业务验证通过。`partial` 表示计划内只有部分写入/引用完成，必须列已完成与待修复项。流程被否定时记录来源和继任版本，不静默删除历史理由。

## 按已有授权落地

授权依据是当前用户指令或适用的持续约定，本文件本身不能向其他使用者授予权限。当前用户已经明确采用本约定时直接执行，不重复确认。

- 当前流程相关的用户通用/专用 Skill、必要的新通用 Skill，以及绑定库内经验/案例/索引：本用户已授权联合反思时直接维护，不逐条再问。改动收敛到实际目标，不能借机改造全部 Skill。新建/修改调用当前可用 skill-creator 并按本地规则校验、独立评价和限定范围 Git 同步。
- 托管插件、系统 Skill、只读或其他所有者的资源按其实际权限处理；不能直接覆盖。无关 Skill、全局指令和真实业务不在本授权内。只有 Git 同步授权本身仍不能推出任意维护权；这里相关维护权来自用户明确的流程沉淀要求。
- 范围外的目标：先保存精确的最小补丁及依据，标 `proposed`，不应用；可在获准库中完成经验和其他流程更新，不因这一项停掉整个闭环。
- 不借优化之名更换用户产品、删强制要求、绕过安全停止，或修改全局指令/凭据/系统权限。原任务未提供验收证据时，不用“更顺畅”的主观描述替代。

## 一致性、冲突和恢复

采用现有单写者/锁/事务契约。写前核对 base_revision/hash；变了就重读并重新核对，不覆盖他人的更新。无可靠协调时只产候选，由一个写入者合并。

先列本轮计划触及的目标和链接，再保存最少差异；双向关系和索引应在同一轮完成。多文件保存不是天然事务：若某一步失败，记录 `partial`、哪些文件已写、剩余动作及同一轮标识；下一次按该标识补缺，不重复造卡或新流程。不要回滚/覆盖已有的无关改动。

修改后检查实际目标内容、ID/版本、步骤与经验链接、索引可达性和原有必需检查。经验有效但流程相反，或流程变了却仍引用已否定证据时，保留冲突状态并停止套用该分支，先补权威依据。

必要时用脱敏夹具验证新顺序/异常分支，并保留旧流程仍适用的反例作回归。文字检查、隔离回放、真实业务验证和长期收益分别报告，不能为测试再次创建真实资源。

## 下一次如何使用

新任务从经验与 Skill 发现入口检索，读到对应章节/步骤的条件与证据后执行，写采用/不采用及真实结果。旧配置没有 workflow_index 时仍可发现并更新 Skill；旧卡和原有流程文档链接保留为案例/历史，不要求重建库。

如果本轮两侧无持久化价值，就保留当前任务的简短处理结果；若只有一侧需要变，另一侧明确 `unchanged` 及原因。联合沉淀不是强制双倍文件或固定条数。
