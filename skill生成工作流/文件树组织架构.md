# 结论

你需要的不是以 Git 提交检查为核心的 `repo-structure-guardian`，而是一个以**项目类型识别、标准项目树生成和文件位置规划**为核心的：

> **`project-structure-architect`（项目结构架构师）Skill**

该 Skill 应当完成三个核心任务：

1. **新项目初始化**：识别 Web、科研、数据科学、机器学习、后端服务、Monorepo 等项目类型，生成对应的标准项目树。
    
2. **开发过程维护**：创建页面、接口、模型、实验步骤或脚本前，先判断文件应放在哪一层。
    
3. **现有项目治理**：读取现有结构，延续已有规范，不随意新建同义目录或把文件堆在根目录。
    

其中“防止乱提交”只是附属功能，核心应是：

```text
项目需求
   ↓
识别项目类型
   ↓
选择目录蓝图
   ↓
根据技术栈调整
   ↓
生成项目树
   ↓
记录目录职责
   ↓
后续文件按职责路由
   ↓
检查实际结构是否偏离蓝图
```

# 2. Skill 的核心不应是“一套固定目录”

不存在适合所有项目的唯一目录树。正确策略是建立：

> **项目类型分类器 + 目录蓝图库 + 文件位置路由器**

推荐决策矩阵如下。

|项目类型|推荐根结构|主要依据|
|---|---|---|
|前后端分离 Web|`frontend/ + backend/`|前后端技术栈不同或可独立部署|
|TypeScript Monorepo|`apps/ + packages/`|多应用、公共 UI、类型和配置复用|
|微服务项目|`services/ + packages/ + infra/`|多个独立部署服务|
|科研项目|`data/ + steps/ + src/ + experiments/ + outputs/ + paper/`|强调研究步骤和可复现性|
|数据科学项目|`data/raw/interim/processed + notebooks + src + models + reports`|数据生命周期分层|
|Python 库|`src/<package>/ + tests/ + docs/`|避免导入路径污染|
|单体后端|`app/api + services + repositories + models + schemas`|分离接口、业务和数据访问|
|前端单项目|`app + features + components + lib + assets`|按功能组织而非按文件类型堆积|

```text
│   │   ├── hooks/
│   │   ├── stores/
│   │   ├── lib/
│   │   ├── assets/
│   │   └── styles/
│   ├── tests/
│   ├── package.json
│   └── README.md
│
├── backend/
│   ├── app/
│   │   ├── api/
│   │   │   ├── routes/
│   │   │   └── dependencies/
│   │   ├── core/
│   │   ├── services/
│   │   ├── repositories/
│   │   ├── models/
│   │   ├── schemas/

```

FastAPI 官方全栈模板直接采用根级 `backend/` 和 `frontend/` 分离，并分别维护开发文档；该仓库在本次检索时约有 44.2k Star。([GitHub](https://github.com/fastapi/full-stack-fastapi-template "GitHub - fastapi/full-stack-fastapi-template: Full stack, modern web application template. Using FastAPI, React, SQLModel, PostgreSQL, Docker, GitHub Actions, automatic HTTPS and more. · GitHub"))

目录名称建议使用 `frontend`，而不是缩写 `front`。除非现有项目已经统一使用 `front`，否则完整名称更明确。

## 3.2 前端内部应按功能域组织

`features/` 不是存放所有组件，而是存放完整业务功能：

```text
features/
└── authentication/
    ├── api/
    ├── components/
    ├── hooks/
    ├── routes/
    ├── stores/
    ├── types/
    ├── utils/
    └── index.ts
```

`Bulletproof React` 将前端划分为 `app`、`assets`、`components`、`config`、`features`、`hooks`、`lib` 等层级，强调清晰边界和可扩展性；本次检索时约有 35.5k Star。([GitHub](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md?utm_source=chatgpt.com "project-structure.md - alan2207/bulletproof-react"))

Skill 应强制区分：

```text
仅一个业务功能使用   → features/<feature>/
全局通用 UI         → components/ui/
跨功能通用组件       → components/common/
第三方库封装         → lib/
后端请求封装         → services/ 或 features/<feature>/api/
全局状态             → stores/
静态资源             → assets/
```

## 3.3 TypeScript Monorepo：使用 `apps/ + packages/`

当存在多个前端、Node.js 后端或共享包时：

```text
project-root/
├── apps/
│   ├── web/
│   ├── admin/
│   ├── api/
│   └── docs/
│
├── packages/
│   ├── ui/
│   ├── types/
│   ├── api-client/
│   ├── validation/
│   ├── config-eslint/
│   ├── config-typescript/
│   └── testing/
│
├── infrastructure/
├── scripts/
├── docs/
├── package.json
├── pnpm-workspace.yaml
└── turbo.json
```

Vercel 的 Turborepo 仓库已经提供正式的 `turborepo` Skill，并将 Monorepo 结构、内部包、应用边界和依赖约束纳入 Skill；其标准结构使用 `apps/*` 与 `packages/*`。本次检索时 Turborepo 约有 30.7k Star。([GitHub](https://github.com/vercel/turborepo/blob/main/skills/turborepo/SKILL.md "turborepo/skills/turborepo/SKILL.md at main · vercel/turborepo · GitHub"))

因此推荐规则为：

```text
可独立启动或部署      → apps/
可被多个应用依赖      → packages/
仅某个应用内部使用    → apps/<app>/src/
共享类型              → packages/types/
共享 UI               → packages/ui/
共享工程配置          → packages/config-*/
```

# 4. 科研项目的推荐结构

科研项目不能简单照搬普通 Python 工程。推荐同时保留：

- **数据生命周期目录**
    
- **研究执行步骤目录**
    
- **可复用源代码目录**
    
- **实验记录目录**
    
- **论文与成果目录**

## 4.2 `steps/` 和 `src/` 必须严格分工

这是防止科研项目后期混乱的关键。

```text
steps/ 负责：
- 表达研究执行顺序
- 读取参数
- 调用 src 中的函数
- 定义输入和输出
- 提供单步骤执行入口

src/ 负责：
- 数据处理算法
- 模型定义
- 特征工程
- 评价指标
- 绘图函数
- 可复用业务逻辑
```

错误方式：

```text
steps/05_model_training/train_model.py
```

里面包含数千行数据读取、网络定义、训练、评价和绘图逻辑。

正确方式：

```python
# steps/05_model_training/run.py

from project_name.models.training import train_model
from project_name.config import load_config

config = load_config("configs/experiments/baseline.yaml")
train_model(config)
```

即：

> `steps/` 表示工作流顺序，`src/` 表示代码职责。

## 4.3 数据目录应按照生命周期分层

Cookiecutter Data Science 使用：

```text
data/
├── external/
├── raw/
├── interim/
└── processed/
```

并使用编号 Notebook 表达分析顺序，例如 `1.0-initial-data-exploration`。该仓库本次检索时约有 9.9k Star。([GitHub](https://github.com/drivendataorg/cookiecutter-data-science "GitHub - drivendataorg/cookiecutter-data-science: A logical, reasonably standardized, but flexible project structure for doing and sharing data science work. · GitHub"))

因此建议 Skill 明确规定：

```text
raw        原始数据，只读、不可覆盖
external   外部机构或第三方数据
interim    中间处理结果，可以重新生成
processed  最终建模或统计分析输入
```

## 4.4 复杂科研流程可借鉴 Kedro

Kedro 将研究或数据流程拆分成独立 Pipeline，每个 Pipeline 中通过 `nodes.py` 定义计算节点，通过 `pipeline.py` 定义执行关系，并将参数放在独立配置文件中。Kedro 强调可复现、可维护和模块化，本次检索时约有 10.9k Star。([Kedro Docs](https://docs.kedro.org/en/stable/tutorials/create_a_pipeline/?utm_source=chatgpt.com "Create a pipeline -"))

因此科研蓝图可以进一步采用：

```text
src/project_name/pipelines/
├── data_processing/
│   ├── nodes.py
│   └── pipeline.py
├── feature_engineering/
├── model_training/
└── evaluation/
```

对于简单课程科研项目，使用 `steps/` 更直观；对于大型数据流水线，使用 `pipelines/` 更合适。

# 5. 推荐的项目识别规则

`detect_project.py` 不应只检查编程语言，而应同时判断以下维度：

```text
1. 项目用途
   Web / API / 科研 / 数据分析 / 机器学习 / 库 / CLI

2. 技术栈
   React / Vue / Next.js / FastAPI / Django / Spring / Python

3. 部署单元
   单体 / 前后端分离 / 多应用 / 微服务

4. 仓库模式
   单项目 / Monorepo / Polyglot Monorepo

5. 工作流特征
   是否存在连续数据处理步骤
   是否存在实验和模型
   是否需要生成论文和图表

6. 现有规范
   是否已有 frontend、backend、apps、packages、src、steps
```

推荐识别标志：

```text
package.json + vite.config.*           → 前端项目候选
package.json + turbo.json              → TypeScript Monorepo
frontend/ + backend/                   → 前后端分离项目
pyproject.toml + FastAPI               → Python API
data/ + notebooks/ + models/           → 数据科学或科研项目
experiments/ + checkpoints/            → 机器学习实验项目
Snakefile                               → Snakemake 科研工作流
src/*/pipelines/                        → 数据流水线项目
paper/ + references/ + figures/        → 论文型科研项目
```

如果识别结果不唯一，Skill 不应随意套模板，而应选择最保守的结构，并在生成报告中记录推断依据。

# 6. 可直接使用的 `SKILL.md` 核心版

以下内容适合作为 Skill 入口，详细目录蓝图继续放在 `references/blueprints/` 中。

---

## name: project-structure-architect  
description: Design, generate, maintain, and audit project directory structures based on project type, technology stack, deployment model, research workflow, and existing repository conventions. Use when creating a new project, planning a project tree, adding modules or features, separating frontend and backend, organizing research steps, creating experiments or pipelines, restructuring directories, deciding where a file belongs, or reviewing whether a repository structure remains consistent.

# Project Structure Architect

Create and maintain project structures in which every directory has a clear responsibility and every file has a justified location.

## Mandatory activation

Use this skill when:

- Initializing a new project
    
- Designing or documenting a project tree
    
- Adding a frontend, backend, service, application, package, research step, pipeline, experiment, or major module
    
- Creating files when their destination is not already obvious
    
- Refactoring repository structure
    
- Organizing a research, data science, or machine-learning project
    
- Reviewing directory consistency
    

## Primary responsibilities

This skill must:

1. Detect the project category.
    
2. Detect the technology stack.
    
3. Determine deployment and repository boundaries.
    
4. Select the closest project blueprint.
    
5. Adapt the blueprint to actual requirements.
    
6. Explain every top-level and important second-level directory.
    
7. Generate or update `PROJECT_STRUCTURE.md`.
    
8. Route future files to the correct directory.
    
9. Detect structural drift without forcing unnecessary rewrites.
    

## Sources of truth

Apply rules in this order:

1. Explicit user requirements
    
2. Existing repository conventions
    
3. Applicable `AGENTS.md`
    
4. Existing `PROJECT_STRUCTURE.md`
    
5. Existing `.project-structure.yaml`
    
6. Selected project blueprint
    
7. Framework conventions
    

Never replace a coherent existing convention solely because another blueprint is preferred.

## Project classification

Classify the repository across these dimensions:

- Purpose:
    
    - web application
        
    - frontend application
        
    - backend service
        
    - API
        
    - monorepo
        
    - microservices
        
    - research
        
    - data science
        
    - machine learning
        
    - library
        
    - CLI
        
- Deployment:
    
    - single deployable
        
    - frontend/backend independently deployable
        
    - multiple applications
        
    - multiple services
        
- Workflow:
    
    - request-response application
        
    - scheduled jobs
        
    - data pipeline
        
    - ordered research steps
        
    - experimental workflow
        
- Repository:
    
    - single project
        
    - language monorepo
        
    - polyglot monorepo
        

## Blueprint selection

Use the closest blueprint from `references/blueprints/`.

Default mapping:

- Polyglot full-stack web:  
    `web-fullstack-separated.md`
    
- JavaScript or TypeScript monorepo:  
    `web-typescript-monorepo.md`
    
- Frontend-only React project:  
    `react-frontend.md`
    
- Python backend:  
    `python-backend.md`
    
- Ordered scientific research:  
    `research-step-based.md`
    
- General data analysis:  
    `data-science.md`
    
- Modular ML or data pipeline:  
    `machine-learning-pipeline.md`
    

Do not combine multiple blueprints without documenting the reason.

## Web project rules

For independently deployable frontend and backend systems:

- Use `frontend/` and `backend/`.
    
- Keep their dependencies, tests, configuration, and documentation local.
    
- Put API contracts in `contracts/` when shared.
    
- Put deployment configuration in `infrastructure/`.
    
- Organize frontend business logic by feature.
    
- Separate backend API, business services, repositories, schemas, models, and database code.
    

For JavaScript or TypeScript monorepos:

- Put deployable applications in `apps/`.
    
- Put shared libraries in `packages/`.
    
- Do not place application-specific code in shared packages.
    
- Do not create a package until at least one clear consumer exists or the package represents an explicit architectural boundary.
    

## Research project rules

Research projects should normally separate:

- `data/` for data lifecycle
    
- `steps/` for ordered execution stages
    
- `src/` for reusable implementation
    
- `experiments/` for experiment-specific configurations and records
    
- `notebooks/` for exploration and prototyping
    
- `outputs/` for generated results
    
- `paper/` for manuscripts and supplementary materials
    
- `tests/` for reproducibility and correctness
    

`steps/` expresses workflow order. It must not become the primary location for reusable algorithms.

Each step should normally contain:

- an entry point
    
- step-specific configuration
    
- a README describing inputs, outputs, dependencies, and execution
    

Reusable processing logic belongs in `src/`.

## File placement procedure

Before creating a file, determine:

1. What responsibility does the file have?
    
2. Which application, service, feature, research step, or domain owns it?
    
3. Is it reusable or local?
    
4. Is it source code, configuration, data, output, documentation, or test code?
    
5. Does an existing directory already represent this responsibility?
    
6. What imports, inputs, and outputs will it have?
    
7. What file should be tested or documented alongside it?
    

Create the file only after identifying one justified destination.

## Directory creation rules

Do not create a new directory merely because no current directory name looks perfect.

Before adding a directory:

1. Search for an existing equivalent responsibility.
    
2. Check naming and hierarchy conventions.
    
3. Confirm that the directory will contain a coherent category of files.
    
4. Confirm that the directory is not only for one temporary file.
    
5. Document its purpose if it changes the project blueprint.
    

Avoid ambiguous directories such as:

- `misc/`
    
- `temp/`
    
- `others/`
    
- `new/`
    
- `backup/`
    
- unscoped `common/`
    
- unscoped `utils/`
    

## Existing repository behavior

When working in an existing repository:

- Preserve coherent conventions.
    
- Extend repeating patterns.
    
- Do not reorganize unrelated modules.
    
- Do not introduce `frontend/` and `backend/` if the repository already consistently uses `apps/web` and `apps/api`.
    
- Do not introduce numbered research steps if the repository already uses a pipeline framework.
    
- Report structural problems separately from the requested change.
    

## Required project documentation

For a new or substantially reorganized project, generate `PROJECT_STRUCTURE.md` containing:

1. Project classification
    
2. Selected architecture
    
3. Directory tree
    
4. Directory responsibility table
    
5. File placement rules
    
6. Naming conventions
    
7. Dependency directions
    
8. Instructions for adding:
    
    - a new feature
        
    - a new API
        
    - a new service
        
    - a new research step
        
    - a new experiment
        
9. Generated and ignored directories
    
10. Structural decisions and exceptions
    

## Audit procedure

When auditing a repository:

1. Compare the actual tree with the documented blueprint.
    
2. Detect duplicate or synonymous directories.
    
3. Detect source files at inappropriate hierarchy levels.
    
4. Detect mixed source code, generated outputs, data, and documentation.
    
5. Detect reusable logic trapped inside scripts or research steps.
    
6. Detect application-specific code placed in shared packages.
    
7. Detect directories without a coherent responsibility.
    
8. Recommend minimal, migration-safe corrections.
    

Do not automatically move large numbers of files unless explicitly requested.

## Completion output

Report:

- Detected project type
    
- Detected technology stack
    
- Selected blueprint
    
- Generated or updated directory tree
    
- Purpose of each important directory
    
- Placement decisions
    
- Existing conventions preserved
    
- Structural risks
    
- Recommended next actions
    

实际使用时，建议把 Web、科研和数据科学的完整目录树拆入独立蓝图，避免 `SKILL.md` 过长。后续可按实际仓库类型裁剪为 Web 专版和科研专版。

# 10. 验收标准

```text
[通过] React + FastAPI 新项目生成 frontend/backend 结构
[通过] TypeScript 多应用项目生成 apps/packages 结构
[通过] 科研项目生成 data/steps/src/experiments/outputs/paper
[通过] steps 仅保存执行入口，核心算法位于 src
[通过] 新增 React 功能时放入对应 features/<feature>
[通过] 新增科研阶段时自动创建编号目录和 README
[通过] 现有 apps/packages 项目不会被强制改成 frontend/backend
[通过] 每个重要目录都有明确职责说明
[通过] 能根据文件职责给出唯一推荐路径

[失败] 所有项目统一生成同一套目录
[失败] Web 前端、后端和部署文件混在根级 src
[失败] 科研脚本、模型、数据和图表全部放在 steps
[失败] 无理由创建 common、utils、misc、temp
[失败] 为了套模板而大规模重构已有规范清晰的仓库
```
