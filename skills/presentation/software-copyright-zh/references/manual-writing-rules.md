# 操作手册写作规则

## 读者与内容

手册面向软件使用者，以真实页面和操作流程说明软件用途、进入路径、可见内容、用户动作、输入/状态限制、异常提示、结果反馈和对应截图。不要写成研发日志、技术设计、API 文档、论文或营销文案。

每个章节必须关联 `source-evidence-map.json` 中 `confirmed` 的真实功能。`partial` 功能只能进入待确认草稿，`unsupported` 功能禁止进入手册。

## 表达方式

- 把页面用途、进入位置、用户动作、限制、异常和结果合并为自然、连续、正式的段落。
- 不重复输出“进入方式：”“页面内容：”“操作步骤：”“操作结果：”等字段模板。
- 不使用“赋能、旨在、一站式、智能化、高效便捷、显著提升、强大能力”等空泛口号。
- 不出现 AI 身份、写作过程、审核技巧或代办承诺。
- 相近功能按真实对象、动作和反馈分别写，不用同一段话替换模块名。
- 章节结构由项目证据和用户确认的 `manual_modules` 决定，不固定套用旧项目骨架。

## 截图

截图引用必须能在截图清单中找到文件、页面、路径、前置数据、动作、证明功能、采集方式和时间。不得使用 AI 生成图、设计稿或隐瞒修改的数据冒充运行界面。

草稿阶段可用结构化缺失项记录尚未采集的截图；正式文档不得残留“待补充”“此处略”“后续实现”等占位文字。用户选择跳过截图时，最终清单必须判为未达到最终提交状态。

## 信息不足处理

1. 在草稿自检记录中列出缺失事实和对应证据。
2. 停止正式生成或将最终状态保持为 `BLOCK`。
3. 向用户询问具体事实，不用常见方案补写。
4. 用户补充后重新运行一致性和输出校验。

## 自检

- 章节是否都能追溯到真实功能。
- 名称、版本、功能和截图是否一致。
- 是否出现重复模板句、技术化口吻、营销套话或未实现功能。
- 是否写清输入限制、异常提示和操作结果。
- 是否存在占位文字、空章节、模板残留或敏感信息。

`草稿自检记录.md` 必须包含 `status: PASS`、`reviewer`、ISO-8601 `reviewed_at`，以及 `evidence_mapping`、`natural_language`、`no_template_marketing`、`screenshot_mapping`、`sensitive_data` 五项 `PASS`。手册至少包含两个有实质内容的自然段；字段模板句、营销词和重复段落直接阻断。
