## 目标与本轮边界

用户要求（2026-11-02）：所有 Skill 有状态；执行前确认其中工具和资料齐备；先拉取 Skill，优化验证后推送；复盘 REA 的缺依赖案例。

目录判定：复用 `.agents/skills/guardrail/<skill>/` 的现有惯例；源码和测试进入本 Skill `scripts/`，协议和验收进入 `references/`，全库机器状态进入忽略的 `.agents/.local/skill-readiness/`。检测器无法识别技能仓库类型（CAUTION），结合根规则和已存在的 guardrail/scripts/references 惯例完成只增本职责目录的人工判定，不套 Python 工程蓝图、不移动游戏文件。

## 五个致命痛点

1. **假就绪**：只见 SKILL.md 或命令路径便通过，运行时仍失败。否决：不兼容版本或失败探测能得到 READY。修正：版本与实际只读探测分开；会话能力单独查。
2. **漏依赖**：关键词抽取漏掉工具、模板或数据。否决：自动生成空清单便通过。修正：自动草案保持未审阅，绑定完整包指纹；所有未分类项为未知。
3. **旧状态冒用**：升级、换机、换会话后仍沿用绿灯。否决：改材料或换会话仍通过。修正：调用时重算、重查，检查时间与会话身份写入证据。
4. **分支冒充全量**：只装 Ghidra 就说 REA 所有工具齐备。否决：分支检查写出 full_skill_ready=true。修正：默认 full，缩小范围需明确理由且保留未选项目。
5. **入口漏接或供应商覆盖**：只改 router，直接调用绕过；或改插件缓存被升级覆盖。否决：直接入口不要求检查。修正：用户全局规则覆盖所有来源，受维护入口直接接入，供应商使用外置清单。

## 三轮修订

- 第 1 轮：由“统一状态标签”修订为“清单＋真实检测＋失败阻断”；消除纯文字状态，依赖完整性仍黄灯。
- 第 2 轮：加入未审阅默认未知、材料闭包、指纹与远程材料分类；将完整性风险变成显式阻断，跨平台范围仍黄灯。
- 第 3 轮：保留 full 与明确分支双状态；全局入口覆盖第三方和 system，机器状态不推仓库；进入测试与独立评审，测试失败或评审阻断则继续修订。
