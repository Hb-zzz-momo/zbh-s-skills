# 非商用与比赛软件：开源底座优先

这是该用户的软件选型偏好：先找同类开源底座，验证后复用，再添加用户需要的规则。人数少、非商用或比赛用途不能成为降低交付质量的理由；用户明确要求自研或指定仓库时优先遵从。

## 选型与落地

1. 从原始请求列出必需功能、业务规则、真实使用流程及不能改变的数据、接口和部署边界。已有可运行系统先核对当前状态，避免凭历史印象选型。
2. 检索相关项目的一手仓库和文档，按需求覆盖与实际可维护性筛选。样本数量随问题调整；记录仓库 URL、检查日期、固定 tag/commit、维护情况、技术栈和已发现限制。星数、搜索摘要、演示站和赞助广告不能证明功能或稳定性。
3. 核对固定版本的 LICENSE、NOTICE、第三方依赖及适用要求。比赛项目先检查提供的比赛规则、外部代码允许范围和原创性要求；没有规则时明确待核实，不能承诺可提交。区分代码使用许可、上游服务授权与数据/素材权限，非商用不自动免除义务。
4. 比较候选复用、已有系统增量改造及必要自研：需求覆盖、缺口、维护与迁移成本、安全隔离、依赖和回滚。没有合适底座、许可不兼容、比赛禁止、实测失败或改造成本明显更高时，可以自研，并记录具体证据；不强行为了复用改变用户目标。
5. 选定后先验证最高风险的完整流程：真实入口、权限、正常和异常路径、用量/计费等核心规则。将仓库宣称、源码已证实、实际已验证及未验证分别记录。只读页面或端口成功不能支持完整可行结论。
6. 继承底座的结构和升级方式，优先通过配置、已有扩展点、适配器或范围清晰的补丁加入差异规则。保留上游来源与署名，清楚区分底座能力和本次新增工作；不把 fork 包装成独立原创。
7. 按任务所需的规格、设计、测试和部署流程完成交付。需求或定位改变时重新检查选型假设；迁移先备份并验证恢复，替代关键流程通过前保持可回滚。技能偏好本身不授权上传代码、创建外部资源或替用户接受条款，外部动作按本次用户授权执行。

## 最小交付证据

- 选型结论：固定上游版本、采用理由、主要取舍、许可/比赛规则检查结果和未验证项。
- 需求追踪：要求 → 底座已有能力/定制修改 → 验证证据 → 当前状态。
- 实际成果：可运行软件、配置和操作说明、适当的真实流程验证、部署/迁移与回滚方法。
- 来源与差异：保留必要声明，列出定制点，交付包排除凭据、个人数据和运行数据库。

不要止步于候选名单或方案；在已授权范围内推进到用户要求的运行和交付状态。读取本技能、拥有规格文件或测试局部通过，都不能代替全部必需目标的完成证据。
