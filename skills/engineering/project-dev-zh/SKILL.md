# 项目理解与工程开发技能
<!-- project-structure-architect:gate:v1:start -->
## Project structure gate / 文件树结构门禁

只要本工作流将初始化或重组项目，或新建、移动应用、服务、包、模块、页面、API、研究步骤、实验、流水线、测试、文档或多文件产物树，必须先使用 `project-structure-architect`。

1. 开始前：读取适用的 `AGENTS.md`、`PROJECT_STRUCTURE.md`、`.project-structure.yaml` 和现有文件树，锁定项目类型、蓝图及唯一合理路径。
2. 运行中：每次新增或移动文件前先判断职责、所有者、复用范围和对应测试；禁止同义目录、根目录堆放、跨层混放及无关重组。
3. 阶段收口：纵向切片或阶段完成后检查结构漂移；新项目或重大重组更新结构文档，最终运行结构审计。出现 `BLOCK` 时停止结构性写入并先修正或询问用户。

纯内容编辑且目标路径已由用户或现有规范唯一确定时，可不重复调用。

## 技能目标

提供从“技术知识问答→代码阅读→项目理解→链路追踪→工程开发”的完整支持。回答知识性问题时，让零基础用户先抓住结论，再通过统一类比、必要术语、真实现状和判断依据形成完整理解；修改工程时，确保先理解现有实现再做高质量增量修改。

## Markdown 交付要求

1. 使用本技能完成正式输出时，除聊天中的简要说明外，必须在当前工作区新建一个 Markdown 文档保存完整结果。
2. 默认保存位置为当前工作区 `skill-outputs/project-dev-zh/`（与 `artifact-curator-zh` 按技能分子目录一致；根目录为 **legacy-flat** 兼容）。若该子目录不存在须先创建。
3. 默认文件名格式为 `中文主题_YYYYMMDD_HHMMSS.md`（置于上述目录下；文件名不再重复 skill 名）；若主题不明确，使用 `结果_YYYYMMDD_HHMMSS.md`。
4. Markdown 文档必须包含完整代码分析、架构说明、链路追踪结果、修改建议或开发方案。
5. 若用户明确指定保存路径或文件名，以用户要求为准；若用户明确要求只在对话中回答，可跳过创建文件。
6. 最终回复中要说明新建的 Markdown 文件路径（须含 `skill-outputs/project-dev-zh/` 前缀），以及文件里包含的主要内容。
7. 模式E的单一知识问答默认直接在对话中完整回答，不为每个概念机械创建文件；只有用户要求保存、问题形成多文件项目审计，或答案需要作为正式可复用报告交付时，才写入上述 Markdown 路径。

| B. 项目架构解析 | "解析项目结构""梳理架构""这个项目怎么组织的" | 分层架构 + 模块关系 |

## 模式A：代码理解（4级递进）

### V1 —— 主干速览

> 目标：30秒内知道这段代码"做了什么"

输出：
1. 一句话总结功能
2. 输入是什么 / 输出是什么
3. 核心数据结构

### V2 —— 逻辑拆解

> 目标：能向别人讲清楚"怎么做的"

输出：
1. 分步拆解主要逻辑流程
2. 关键分支与边界条件
3. 调用了哪些外部依赖
4. 用一段话的类比解释核心思想

### V3 —— 设计意图

> 目标：理解"为什么这样写"

输出：
1. 设计模式识别（如有）
2. 性能/可维护性/安全性的权衡
3. 可能的替代方案及其取舍
4. 潜在的坑/隐患

### V4 —— 可修改性评估

> 目标：判断"能改什么、改了会影响什么"

输出：
1. 修改热区（最可能需要改动的地方）
2. 耦合分析（改这里会影响哪些地方）
3. 测试覆盖建议
4. 安全修改路径推荐

### 使用规则

- 用户未指定级别时，默认输出 V2
- 用户说"详细"时输出到 V3
- 用户说"我想改它"时直接跳到 V4
- 每级都要标注对应的代码行号

### 代码教学增强规则

- 当用户要求"逐行讲解""解释这行语法""用初学者方式讲""把这段代码展开讲"时，仍使用模式A，但输出必须切换为"语法 + 业务"双线讲解。
- 输出顺序优先为：`名词速览 → 原代码片段 → 语法解释 → 本段业务作用 → 等价展开写法 → 整体执行流程`。
- 名词速览只列本段理解必需的术语，避免把不相关概念堆成词典。
- 名词速览不能只给通用定义，必须补上“它在当前函数 / 当前方法签名 / 当前调用点 / 当前会话里的具体作用”。
- 如果术语是变量、参数、配置项、装饰器、返回类型或对象成员，优先解释它在本地上下文中影响了什么，而不是先讲教科书定义。
- 对知识点、术语和语法点的解释，都要补一个**简单例子**帮助理解；例子优先 1-3 行的小片段或一句生活化对照，不要上来就给复杂业务样例。
- 语法解释必须绑定当前代码片段，回答"这行代码怎么写出来的、为什么这里这样写"，不能只给抽象定义。
- 遇到列表推导式、条件表达式、切片、zip 解包、with 上下文、类型注解等压缩写法时，优先给出等价的 `for/if/普通赋值` 展开版。
- 相同语法第一次详细解释，后续重复出现时只补充本处差异，避免逐行机械重复。
- 如果这段代码还承担链路中的一跳，要顺手说明"这一跳从上游拿到了什么、往下游交出了什么"，但不要把语法讲解完全替换成链路图。

## 模式B：项目架构解析

### 分析步骤

1. **目录结构扫描**——识别分层（controller/service/dao/model 等）
2. **入口识别**——找到 main / app / 启动文件
3. **模块划分**——按业务域/技术层分组
4. **依赖关系**——模块间调用关系
5. **配置识别**——环境变量、配置文件、数据库连接
6. **链路分级**——按主链 / 辅读链 / 支撑链分类，不要一上来深挖底层

### 输出格式

```
项目名称：XXX
技术栈：XXX
分层结构：
  ├── 路由层（controller/router）
  ├── 业务层（service）
  ├── 数据层（dao/repository/mapper）
  └── 模型层（model/entity）
核心模块：[列表]
模块间依赖：[描述]
启动方式：XXX
```

## 模式C：后端链路分析

### 链路追踪模板

从请求入口追踪到数据库，完整覆盖：

```
请求 → 路由（route/controller）
     → 中间件（auth/validation）
     → Service（业务逻辑）
     → Repository/DAO（数据操作）
     → 数据库（SQL/ORM）
     → 返回数据组装
     → 响应
```

### 每一层输出

| 层 | 输出内容 |
|----|----------|
| 路由 | URL + HTTP方法 + 参数校验规则 |
| 中间件 | 鉴权方式 + 异常拦截 |
| Service | 核心业务逻辑 + 事务边界 |
| DAO | SQL/ORM调用 + 表名 + 字段映射 |
| 数据库 | 表结构 + 索引 + 关联关系 |

### 输出格式

- 用「→」符号连接各层
- 每层标注对应文件路径和行号
- 数据变换处标注字段映射

## 模式D：工程化开发

### 开发前必做

1. **先读后写**——先理解现有代码结构，再动手
2. **确认影响面**——列出本次修改涉及的文件和模块
3. **确认接口契约**——入参/出参/错误码/状态码

### 编码规范

1. **命名保持一致**——变量名、函数名、文件名风格跟项目已有代码统一
2. **分层职责清晰**——Controller 不写业务逻辑，Service 不写 SQL
3. **增量修改**——不推倒重来，不改不相关的代码
4. **错误处理**——系统边界处做校验，内部逻辑不过度防御
5. **不留 TODO**——要么做完，要么不做

### 增量修改约束

- 先读现有结构，再改代码
- 禁止推倒重来（除非明确要求）
- 保留兼容旧字段，增加增强层新字段
- 不为了改动小而薄封装，导致逻辑层级越叠越高

### 提交规范

- 每次修改说明：改了什么 / 为什么改 / 影响范围
- 保持项目在任何时候都能跑

## 模式E：知识性问题小白解析

### 回答目标

让没有相关背景的用户先看懂这是什么、为什么这样，再用一个具体例子落地。先给结论，再进入场景，然后讲清因果。数字、文档和技术对象放在它们所证明的判断下面，说明它是在证明、支撑还是改变那个判断。

默认骨架是：一句结论 → 一个具体场景 → 为什么成立 → 容易混的点。章节数由内容决定，一段能讲清就不开第二段；只有用户的问题本身是排查故障时，才需要展开“现状 → 症状 → 修复动作”。

### 回答前判定

1. 先确定用户真正问的是“是什么、怎么工作、为什么这样设计、现在是否落地、是否合理”中的哪一类；多个问题并存时先给总判断，再分层回答。
2. 若问题绑定本地项目、ADR、代码、接口、指标或文档，先读取相关证据；没有证据时明确写“仅作通用解释”或“待项目证据确认”，不得把常识猜测写成项目事实。
3. 先确定这道题真正要回答的判断是什么，再组织材料。项目问题优先使用真实业务流、数据流或交付状态；不要把技术名词排成一串冒充因果，也不要让一条链承载全部信息。
4. 选定一个贯穿全文的具体实例，至少包含“谁、正在做什么、想得到什么结果”。有项目上下文时使用真实对象；没有时明确标注“下面是用于解释的假设例子”，不得当成项目事实。
5. 给每条信息标注它在本题中的关系：`原因` 促成后续结论；`证据` 证明某个判断；`前置条件` 是成立必须具备但未必由上一步产生的条件；`结果` 是前面的后果；`动作` 用于改变现状。同一信息在不同问题里角色不同，写清“它相对于哪个判断是什么”，不要永久贴标签。
6. 若结论包含评价，分开表达：`事实` 是材料直接显示的内容，`推理` 是由事实推出的含义，`评价` 是基于成本、收益、风险或一致性的判断。
7. 根据复杂度选择篇幅：单一概念三到四段即可；涉及多个术语、设计取舍或项目审计时才展开。不要为凑模板重复同一句话。

### 因果关系与证据挂靠

- 只在真实存在因果关系、约束或输入输出关系时使用箭头；仅时间先后或主题接近，不能画成因果。
- 画了箭头就要能补成一句“因为 A，所以 B”“A 使 B 更严重”或“B 必须使用 A 的产物”。补不出来就改成并列或删掉。
- 证据挂在它所证明的判断下面，不单独升级成一章。例如“189 个目标接口、403 个页面”证明规划范围大，“25 个接口接入”证明完成度低，两者都是支撑材料，不是独立章节。
- 多个条件共同决定一个结论时，说明它们共同服务于什么目标、彼此属于“缺一不可但互相独立”“相互影响的耦合条件”还是“可选其一”，不要伪造成先后顺序。

### 标准顺序

1. **先给结论**：第一段直接回答问题，不铺垫、不预告要讲什么。
2. **进入具体场景**：用一个短故事或类比建立直觉，随后把生活角色映射到真实技术对象。全文沿用同一个实例，不中途切换比喻体系。
3. **讲清为什么**：按因果逐层展开，每一步说明理由；术语在首次出现的位置解释。
4. **点出容易混的地方**：成对澄清易混概念，各配一个最小例子。
5. **需要时补一行逻辑链路**：只有内容确实是多步递进时，才在该段末尾补一行 `输入 → 机制 → 输出`。不是每段都要写，也不要重复整篇。
6. **说明当前实际状态**：区分计划、文档、契约、代码、测试和运行结果分别做到哪里；涉及比例、状态码或固定数量时，解释统计口径及“它不代表什么”。
7. **若用户在排查故障**：改用“现状 → 症状 → 根因 → 修复动作 → 验收证据”的顺序，每个动作注明它要改变哪个状态、用什么真实证据验收。

### 单一概念

用户只问一个概念时，不展开完整体系。最少回答三件事：它是什么、它在哪一步介入、介入后结果怎么变。然后补一个最小例子和一个容易误解点。

例如解释 CI：先用“门卫按检查单验货”建立直觉，再固定为“小李提交创建宠物功能”这一实例，说明提交后流水线做了什么、分支因此获得允许或拒绝合并的状态。配置文件、平台和 Runner 是实现条件，不单独拉成知识标题。

### 术语解释硬规则

- 首次出现的英文缩写先给中文名称和一句白话含义，例如 `ADR（架构决策记录）`；后文直接使用缩写。
- 优先解释“这个词在本题里干什么”，再补通用定义；禁止复制百科式定义后不回到当前问题。
- 示例优先复用用户正在讨论的项目对象；若无项目对象，再选一个 1-3 行技术示例或生活例子。
- 对容易混淆的概念成对澄清，例如 Header/Body、Schema/Runtime、模板存在/业务接入、接口未登记/后端完全没有接口。
- 不得在开头设置大段“术语解释”后才讲关系；术语必须嵌入它真正出现的因果节点。
- 不把类比当证据。类比只帮助建立直觉，最终结论必须回到文档、代码、测试、数据或明确的通用规则。

### 输出模板

```markdown
# [主题] 小白解析

## 一句话结论

[直接回答问题 + 最重要的判断]

## 具体场景

[同一生活类比的小故事：谁、在做什么、目标是什么；随后给出生活角色到技术对象的映射。全文沿用这个实例]

## 为什么这样

[按因果逐层说明；证据挂在对应判断下；术语首次出现时解释]

## 容易混的点

[一两个成对澄清 + 最小例子]
```

四段不够用时按内容增加段落，但不要把上面的骨架当成固定章节数，也不要为了凑章节补内容。

### 质量自检

- [ ] 第一段就是答案，不是铺垫、计划或“让我先说明”。
- [ ] 全文沿用同一个实例，没有中途换例子；类比只用于建立直觉，没有被当成证据。
- [ ] 每条箭头都能补成一句因果说明；补不出来的已改成并列或删除。
- [ ] 术语在首次出现的因果位置解释；事实、推理、评价没有混写，结论没有超出证据。

## 自我迭代模式

### 触发条件

当用户在使用本技能后给出反馈（如"这部分不好用""输出格式需要改""多了/少了XX"），或主动说"优化这个skill"时，进入自我迭代模式。

### 迭代工作流

1. **收集反馈**：明确用户不满意的具体环节（哪个模式 / 哪个步骤 / 什么问题）
2. **诊断根因**：是规则缺失、规则冲突、粒度不够、还是场景未覆盖？
3. **提出修改方案**：列出拟修改的条目（原文 → 修改后），说明修改理由
4. **用户确认**：修改方案经用户确认后才执行
5. **写入 SKILL.md**：将修改直接应用到本技能文件
6. **记录迭代日志**：在 `references/iteration-log.md` 追加本次迭代记录

### 迭代日志格式

```markdown
## [日期] 迭代 #N

- **触发反馈**：...
- **根因**：...
- **修改内容**：...
- **影响范围**：模式X / 步骤Y
```

### 迭代约束

- 不破坏现有模式结构——增量修改，不推倒重写
- 每次迭代只改一个关注点——不趁机大改
- 修改后 SKILL.md 总行数仍 < 500
- 重大结构变更（如新增/删除模式）必须用户明确同意
