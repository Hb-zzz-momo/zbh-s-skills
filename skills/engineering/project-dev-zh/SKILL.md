# 项目理解与工程开发技能

## Project structure gate / 文件树结构门禁

只要本工作流将初始化或重组项目，或新建、移动应用、服务、包、模块、页面、API、研究步骤、实验、流水线、测试、文档或多文件产物树，必须先使用 `project-structure-architect`。

1. 开始前：读取适用的 `AGENTS.md`、`PROJECT_STRUCTURE.md`、`.project-structure.yaml` 和现有文件树，锁定项目类型、蓝图及唯一合理路径。
2. 运行中：每次新增或移动文件前先判断职责、所有者、复用范围和对应测试；禁止同义目录、根目录堆放、跨层混放及无关重组。
3. 阶段收口：纵向切片或阶段完成后检查结构漂移；新项目或重大重组更新结构文档，最终运行结构审计。出现 `BLOCK` 时停止结构性写入并先修正或询问用户。

纯内容编辑且目标路径已由用户或现有规范唯一确定时，可不重复调用。

## 技能目标

提供从“技术知识问答→代码阅读→项目理解→链路追踪→工程开发”的完整支持。回答知识性问题时，让零基础用户先抓住结论，再通过统一类比、必要术语、真实现状和判断依据形成完整理解；修改工程时，确保先理解现有实现再做高质量增量修改。

## Markdown 交付要求

1. 使用本技能完成正式输出时，除聊天中的简要说明外，必须在当前工作区新建一个 Markdown 文档保存完整结果。
2. 默认保存位置为当前工作区 `skill-outputs/project-dev-zh/`（与 `artifact-curator-zh` 按技能分子目录一致；根目录为 **legacy-flat** 兼容）。若该子目录不存在须先创建。
3. 默认文件名格式为 `中文主题_YYYYMMDD_HHMMSS.md`（置于上述目录下；文件名不再重复 skill 名）；若主题不明确，使用 `结果_YYYYMMDD_HHMMSS.md`。
4. Markdown 文档必须包含完整代码分析、架构说明、链路追踪结果、修改建议或开发方案。
5. 若用户明确指定保存路径或文件名，以用户要求为准；若用户明确要求只在对话中回答，可跳过创建文件。
6. 最终回复中要说明新建的 Markdown 文件路径（须含 `skill-outputs/project-dev-zh/` 前缀），以及文件里包含的主要内容。
7. 模式E的单一知识问答默认直接在对话中完整回答，不为每个概念机械创建文件；只有用户要求保存、问题形成多文件项目审计，或答案需要作为正式可复用报告交付时，才写入上述 Markdown 路径。

## 模式A：代码理解（4级递进）

### V1 —— 主干速览

> 目标：30秒内知道这段代码"做了什么"

输出：
1. 一句话总结功能
2. 输入是什么 / 输出是什么
3. 核心数据结构

### V2 —— 逻辑拆解

> 目标：能向别人讲清楚"怎么做的"

输出：
1. 分步拆解主要逻辑流程
2. 关键分支与边界条件
3. 调用了哪些外部依赖
4. 用一段话的类比解释核心思想

### V3 —— 设计意图

> 目标：理解"为什么这样写"

输出：
1. 设计模式识别（如有）
2. 性能/可维护性/安全性的权衡
3. 可能的替代方案及其取舍
4. 潜在的坑/隐患

### V4 —— 可修改性评估

> 目标：判断"能改什么、改了会影响什么"

输出：
1. 修改热区（最可能需要改动的地方）
2. 耦合分析（改这里会影响哪些地方）
3. 测试覆盖建议
4. 安全修改路径推荐

### 使用规则

- 用户未指定级别时，默认输出 V2
- 用户说"详细"时输出到 V3
- 用户说"我想改它"时直接跳到 V4
- 每级都要标注对应的代码行号

### 代码教学增强规则

- 当用户要求"逐行讲解""解释这行语法""用初学者方式讲""把这段代码展开讲"时，仍使用模式A，但输出必须切换为"语法 + 业务"双线讲解。
- 输出顺序优先为：`名词速览 → 原代码片段 → 语法解释 → 本段业务作用 → 等价展开写法 → 整体执行流程`。
- 名词速览只列本段理解必需的术语，避免把不相关概念堆成词典。
- 名词速览不能只给通用定义，必须补上“它在当前函数 / 当前方法签名 / 当前调用点 / 当前会话里的具体作用”。
- 如果术语是变量、参数、配置项、装饰器、返回类型或对象成员，优先解释它在本地上下文中影响了什么，而不是先讲教科书定义。
- 对知识点、术语和语法点的解释，都要补一个**简单例子**帮助理解；例子优先 1-3 行的小片段或一句生活化对照，不要上来就给复杂业务样例。
- 语法解释必须绑定当前代码片段，回答"这行代码怎么写出来的、为什么这里这样写"，不能只给抽象定义。
- 遇到列表推导式、条件表达式、切片、zip 解包、with 上下文、类型注解等压缩写法时，优先给出等价的 `for/if/普通赋值` 展开版。
- 相同语法第一次详细解释，后续重复出现时只补充本处差异，避免逐行机械重复。
- 如果这段代码还承担链路中的一跳，要顺手说明"这一跳从上游拿到了什么、往下游交出了什么"，但不要把语法讲解完全替换成链路图。

### 代码教学输出模板

```markdown
## 名词速览

- `术语`：通用含义（一句话）
- 在这里的作用：[它在当前函数/当前调用点里具体做什么]
- 简单例子：[一个最小例子或生活化对照]

## 这段代码整体在做什么

[先用一句话说明方法/片段的业务作用]

```python
[原始代码片段]
```

- `语法点/关键字`：[字面意思]
- 本段作用：[在当前业务里的作用]
- 简单例子：[一个最小可理解例子]
- 等价展开：

```python
[更直白的 if/for/普通写法]
```

## 整段执行流程

1. [步骤1]
2. [步骤2]
3. [步骤3]

## 一句话总结

[把"代码做什么"和"用了哪些关键语法"收束成一句话]
```

## 模式B：项目架构解析

### 分析步骤

1. **目录结构扫描**——识别分层（controller/service/dao/model 等）
2. **入口识别**——找到 main / app / 启动文件
3. **模块划分**——按业务域/技术层分组
4. **依赖关系**——模块间调用关系
5. **配置识别**——环境变量、配置文件、数据库连接
6. **链路分级**——按主链 / 辅读链 / 支撑链分类，不要一上来深挖底层

### 输出格式

```
项目名称：XXX
技术栈：XXX
分层结构：
  ├── 路由层（controller/router）
  ├── 业务层（service）
  ├── 数据层（dao/repository/mapper）
  └── 模型层（model/entity）
核心模块：[列表]
模块间依赖：[描述]
启动方式：XXX
```

## 模式C：后端链路分析

### 链路追踪模板

从请求入口追踪到数据库，完整覆盖：

```
请求 → 路由（route/controller）
     → 中间件（auth/validation）
     → Service（业务逻辑）
     → Repository/DAO（数据操作）
     → 数据库（SQL/ORM）
     → 返回数据组装
     → 响应
```

### 每一层输出

| 层 | 输出内容 |
|----|----------|
| 路由 | URL + HTTP方法 + 参数校验规则 |
| 中间件 | 鉴权方式 + 异常拦截 |
| Service | 核心业务逻辑 + 事务边界 |
| DAO | SQL/ORM调用 + 表名 + 字段映射 |
| 数据库 | 表结构 + 索引 + 关联关系 |

### 输出格式

- 用「→」符号连接各层
- 每层标注对应文件路径和行号
- 数据变换处标注字段映射

## 模式D：工程化开发

### 开发前必做

1. **先读后写**——先理解现有代码结构，再动手
2. **确认影响面**——列出本次修改涉及的文件和模块
3. **确认接口契约**——入参/出参/错误码/状态码

### 编码规范

1. **命名保持一致**——变量名、函数名、文件名风格跟项目已有代码统一
2. **分层职责清晰**——Controller 不写业务逻辑，Service 不写 SQL
3. **增量修改**——不推倒重来，不改不相关的代码
4. **错误处理**——系统边界处做校验，内部逻辑不过度防御
5. **不留 TODO**——要么做完，要么不做

### 增量修改约束

- 先读现有结构，再改代码
- 禁止推倒重来（除非明确要求）
- 保留兼容旧字段，增加增强层新字段
- 不为了改动小而薄封装，导致逻辑层级越叠越高

### 提交规范

- 每次修改说明：改了什么 / 为什么改 / 影响范围
- 保持项目在任何时候都能跑

## 模式E：知识性问题小白解析

### 回答目标

让没有相关背景的用户先进入一个具体场景，再沿着项目或事物的“状态如何一步步变化”理解问题。主链只放真正推动状态变化的判断；数字、文档、技术对象和并行能力放到对应节点下，说明它们是在证明、支撑还是改变该状态。全文持续提醒读者当前位于哪一段，以及局部例子为什么属于这一段。

默认逻辑骨架为：

```text
同一具体场景
→ 状态变化主链
→ 各节点的原因、证据和并行前置条件
→ 局部例子回扣主链
→ 诊断造成的结果
→ 反向对应的解决链与验证证据
```

### 回答前判定

1. 先确定用户真正问的是“是什么、怎么工作、为什么这样设计、现在是否落地、是否合理”中的哪一类；多个问题并存时先给总判断，再分层回答。
2. 若问题绑定本地项目、ADR、代码、接口、指标或文档，先读取相关证据；没有证据时明确写“仅作通用解释”或“待项目证据确认”，不得把常识猜测写成项目事实。
3. 先找一条能够解释核心问题的“状态变化主链”。项目问题优先使用真实业务流、数据流或交付状态；不得要求主链承载全部信息，也不得把技术名词强行排成因果链。
4. 选定一个贯穿全文的具体实例，至少包含“谁、正在做什么、想得到什么结果”。有项目上下文时使用真实对象；没有时明确标注“下面是用于解释的假设例子”，不得当成项目事实。
5. 围绕一个明确的目标状态，先给每条信息标注本题中的关系：`原因` 直接促成后续状态；`证据` 证明某个判断；`前置条件` 是达到目标必须具备但未必由前一步产生的条件；`结果` 是前面状态造成的后果；`动作` 用于改变当前状态。同一信息在不同问题中可能扮演不同角色，分类必须写清“它相对于哪个判断是什么”，不能永久贴标签。
6. 若结论包含评价，分开表达：`事实` 是材料直接显示的内容，`推理` 是由事实推出的含义，`评价` 是基于成本、收益、风险或一致性的判断。
7. 根据复杂度选择篇幅：单一概念用精简链；多个术语、设计取舍或项目审计用完整链；不要为凑模板重复同一句话。

### 状态主链与支撑关系

先从用户目标或系统目标出发，再写状态如何变化。主链节点必须是带主体和判断的状态句，而不是技术对象名：

```text
错误：接口 → OpenAPI → 文件存储 → 可观测性

正确：规划范围快速增加
→ 实际完成能力没有同步增加
→ 已完成部分仍未达到稳定交付标准
→ 用户流程没有闭合
```

每条箭头都必须能补成一句关系说明：“因为 A，所以 B”“A 使 B 更严重”或“B 必须使用 A 的产物”。只有时间先后、主题接近或共同出现，不能使用因果箭头。

证据必须挂到它所证明的状态下。例如“189 个目标接口、403 个页面”共同证明规划范围很大；“25 个接口接入”证明实际完成度较低。它们是支撑节点的证据，不单独升级为主链章节。

多个前置条件若共同服务于一个目标状态，应合并解释，不得伪造先后关系。例如正式接口说明、真实数据保存和错误定位能力，都可能是“稳定交付”的并行条件。回答必须说明它们：

- 共同服务于哪个目标；
- 是“缺一不可但彼此独立”“相互影响的耦合条件”，还是“只需选择其一的替代方案”；
- 为什么没有把它们画成前后因果。

主链因此允许带有支撑分支，整体形态是“状态主链 + 节点证据 + 并行条件”，不是强制直线，也不是无关系的并列清单。

### 标准回答顺序

1. **开头先给贯穿类比和具体实例**：在任何抽象定义之前，用一个短故事说明角色、动作、目标和阻碍，让读者先直觉理解概念。随后立即把生活角色映射到真实技术对象。全文不得切换实例或比喻体系。
2. **紧接着给一句话定位**：直接说明概念位于哪两个环节之间、接收什么输入、输出什么结果。
3. **展示状态路线图**：用同一实例写出 `状态 A → 状态 B → 状态 C`，每条箭头都能说明前者为何引出后者；证据和并行条件暂不冒充路线节点。
4. **按状态逐站展开**：每节标题使用“第 N 站：状态发生了什么变化”，并高亮 `【当前状态】`。先说明上一状态如何导致当前状态，再放证明它的证据。
5. **解释并行支撑**：若当前状态由多个条件共同决定，先说共同目标，再说各条件分别补哪一块、彼此属于哪种并行关系，不使用虚假箭头。
6. **让局部例子往返主链**：例子开始前写明“这个例子用于解释/证明主链第 N 站”；例子结束后写明“因此它让我们确认什么，并为何进入下一站”。禁止讲完模块后不返回整体路线。
7. **在节点首次出现时解释术语**：给出英文全称、中文名称、本节点中的作用和当前实例，不建立脱离主线的术语百科。
8. **定期提醒进度**：链路超过四个节点时，至少每两到三个节点增加一次“到目前为止”小结，说明已经确认哪些状态、还差什么。
9. **说明当前实际状态**：区分计划、文档、契约、代码、测试和运行结果分别做到哪里。涉及比例、状态码或固定数量时，解释统计口径及“它不代表什么”。
10. **建立反向解决链**：每个动作都标注它要改变诊断链中的哪个状态、预期变成什么状态、用什么真实证据验收。允许一个动作同时改善多个状态，但不得留下没有对应动作的核心问题。
11. **最终理解**：回到开头同一实例，复述“状态如何恶化 → 哪些证据和条件证明它 → 动作如何逐步恢复目标状态”，形成闭环记忆。

### 链路路标格式

每个主要章节只保留一行状态导航，再用自然段说明关系：

```text
状态主链：[上一状态] → 【当前状态】 → [下一状态]

因为[上一状态及其作用机制]，所以当前变成[当前状态]；[证据]证明了这一判断。这里的[并行条件 A/B]共同服务于[目标状态]，二者属于[独立共需/相互耦合/互为替代]，不是前后因果。[局部例子]正是在解释本节点；由此才能推出[下一状态]。
```

不是每个节点都必须同时包含证据、并行条件和例子；只写实际存在的关系。若章节只是补充当前节点，不重复整块；切换到新状态时必须更新路标。

### 删除节点测试

删除测试只用于状态主链，不用于证据、术语或并行前置条件。成稿前逐个删除主链节点并检查：

1. 删除中间状态后，如果后一个状态仍能从前一个状态自然推出，该节点不是必要主链，应删除、合并或降为支撑信息。
2. 删除终点节点后，如果最终目标仍然完整形成，终点同样不是主链必要节点。
3. 相邻节点必须存在明确的因果、约束、输入输出或状态恶化关系；不能只存在时间先后。
4. 删除某条证据不会让下一状态失去因果来源，只会削弱判断可信度；删除必要前置条件则会使目标状态无法成立。二者应单独检查，不能据此误判为主链节点。
5. 背景、类比、术语、指标、风险和扩展知识允许作为旁支保留，但不得编号为状态主链节点。

### 单一概念精简链

用户只问一个概念时，不强行展开完整项目体系，至少回答：

```text
具体人物遇到什么问题
→ 状态为什么需要改变
→ 这个概念在哪里介入并产生什么结果
→ 结果如何改变下游状态
```

然后补充一个最小例子和一个容易误解点。例如解释 CI 时，先用“门卫按检查单验货”的故事建立直觉，再固定为“小李提交创建宠物功能”这一实例，沿着“代码尚未经过统一检查 → 提交触发流水线 → Runner 执行测试并形成检查结果 → 分支获得允许或拒绝合并的状态”逐站讲解。配置文件、平台和 Runner 是对应节点中的实现条件，不是三个强行串联的知识标题。

### 术语解释硬规则

- 首次出现的英文缩写先给中文名称和一句白话含义，例如 `ADR（架构决策记录）`；后文直接使用缩写。
- 优先解释“这个词在本题里干什么”，再补通用定义；禁止复制百科式定义后不回到当前问题。
- 示例优先复用用户正在讨论的项目对象；若无项目对象，再选一个 1-3 行技术示例或生活例子。
- 对容易混淆的概念成对澄清，例如 Header/Body、Schema/Runtime、模板存在/业务接入、接口未登记/后端完全没有接口。
- 不得在开头设置大段“术语解释”后才讲关系；术语必须嵌入它真正出现的因果节点。
- 不把类比当证据。类比只帮助建立直觉，最终结论必须回到文档、代码、测试、数据或明确的通用规则。

### 质量自检

- [ ] 开头在抽象术语前给出了可理解的具体类比和角色映射。
- [ ] 全文沿用同一个人物、项目对象和动作，没有中途切换实例。
- [ ] 主链节点都是“主体 + 状态变化”的判断句，不是技术对象或指标名称。
- [ ] 每条箭头都已说明因果、约束、输入输出或状态恶化关系，没有用时间先后冒充因果。
- [ ] 每条信息已相对于目标判断分类为原因、证据、前置条件、结果或动作，没有永久贴标签。
- [ ] 指标和项目事实挂在它们所证明的状态下，没有各自升级为孤立章节。
- [ ] 并行项已说明共同目标及“独立共需、相互耦合或互为替代”的关系，没有强行串成直线。
- [ ] 局部例子开始前说明它对应主链哪一站，结束后回扣该站结论及下一状态。
- [ ] 每次切换节点都高亮当前位置，并说明前一状态为什么引出当前状态。
- [ ] 已对状态节点执行删除测试；证据和前置条件使用各自的检查标准，没有混淆。
- [ ] 长链路包含阶段小结，让读者知道已经完成什么、还差什么。
- [ ] 每个必要术语都在对应节点首次解释，包含当前语境和最小例子。
- [ ] 类比中的角色能映射回真实链路，且没有混用多套比喻或用类比代替证据。
- [ ] 项目事实有本地证据；没有证据的内容已降级为通用解释或待确认。
- [ ] 数字、比例和状态码已解释口径及“不代表什么”。

## 自我迭代模式

### 触发条件

当用户在使用本技能后给出反馈（如"这部分不好用""输出格式需要改""多了/少了XX"），或主动说"优化这个skill"时，进入自我迭代模式。

### 迭代工作流

1. **收集反馈**：明确用户不满意的具体环节（哪个模式 / 哪个步骤 / 什么问题）
2. **诊断根因**：是规则缺失、规则冲突、粒度不够、还是场景未覆盖？
3. **提出修改方案**：列出拟修改的条目（原文 → 修改后），说明修改理由
4. **用户确认**：修改方案经用户确认后才执行
5. **写入 SKILL.md**：将修改直接应用到本技能文件
6. **记录迭代日志**：在 `references/iteration-log.md` 追加本次迭代记录

### 迭代日志格式

```markdown
## [日期] 迭代 #N

- **触发反馈**：...
- **根因**：...
- **修改内容**：...
- **影响范围**：模式X / 步骤Y
```

### 迭代约束

- 不破坏现有模式结构——增量修改，不推倒重写
- 每次迭代只改一个关注点——不趁机大改
- 修改后 SKILL.md 总行数仍 < 500
- 重大结构变更（如新增/删除模式）必须用户明确同意
