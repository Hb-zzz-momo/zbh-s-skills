# 事实变化后的文档联动

仅在本轮确认的变化会影响现行事实、规则、结果或操作路径时读取。复用当前项目入口、事件/阶段记录、单写者和领域验收，不另建全局事实库、强制台账或后台进程；只读任务不写入。三层记忆的 CLI、schema 和五维检查保持原样。

## 1. 先核依据，再作能力结论

评价现有体系或建议新增前，实际读取相关规则、入口和实现，记录所查范围及版本。分清“规则已规定、目标项目已接入、本次实际执行、业务效果已验证”；旧助手结论只能作查找线索。查不到、不可读或未运行写为未核实，不据此断言没有能力。对当前证据互相矛盾的结论回读原件，不重复引用旧摘要。

## 2. 事实变化 → 受影响文档 → 更新结果 → 业务一致性验证

由当前领域主线完成以下交接，三层记忆只负责来源、替代、检索和批次。

1. **事实变化。** 核对旧值、新值、事实来源、适用主体/日期/环境和生效时间。歧义或未经确认的值保持 pending；同一事实替代继续使用新 record id、同 key、supersedes，不覆写历史、不扩大授权。无记忆库时沿用项目既有材料，不自动 init。
2. **受影响文档。** 从当前入口、来源引用、related_ids、managed_files 和既有任务/文档索引定位直接使用者；在本次相关主题内用旧值、别名及相同业务含义补查正文、表格、生成脚本与产物、外发镜像。沿依赖追到直接和间接受影响的位置；不能仅查文件名或登记清单。列出查过的范围、未知入口及可能遗漏，不声称无索引项目已全量覆盖。
3. **更新结果。** 逐项记录位置、依据版本、处理及回读结果，复用既有事件/阶段记录中的简短表格即可。写前重读当前版本；有并行修改则保留双方并处理差异，不能用旧草稿覆盖新稿。只改授权范围的确认关联；不可写、来源不明或外部失联逐项留待办，继续独立工作，不以重试或新 seal 消除缺口。
4. **业务一致性验证。** 根据领域主线的真实目标核对受影响断言与交接，而非只搜索新姓名或比较哈希。对分工核人员可用时段、职责边界、任务/时间/个人视图及接收人；对工程核文档、配置、脚本与真实命令结果；对报告核正文、图表、导出成品和生成源。未知条件不补造；字段齐全、文件保存或工具返回成功均不能代替业务验证。

最小交接记录：

| 变化及来源/适用范围 | 受影响文件及具体位置 | 处理结果/依据版本 | 回读及业务验证证据 | 未完成项与下一步 |
|---|---|---|---|---|

没有新变化不重复扫描或记账。小改只核相关主题、直接依赖及其必要下游；迁移/删除、身份/权限、关键跨文档规则继续遵守原有完整影响检查和领域验收。不得用“增量”或本接口减少已有必选测试、独立评价、教师模板或证据要求。

## 3. 按文件角色处理

| 角色 | 处理 |
|---|---|
| 当前执行稿、总览、现行教程 | 更新适用内容与交接引用，验证与当前事实一致 |
| 内部源稿与导出成品、在线执行版 | 分别记录写入和回读，重生成后检查实际结果，不能相互代证 |
| 历史事件、原始证据、冻结快照 | 保留当时事实；确需更正时按原版本规则另留更正版或替代链接 |
| 通用模板与公共 Skill | 仅方法或普适约束改变时更新；项目姓名、日期、身份和授权不推广为通用规则 |
| 其他环境、主体、日期的相同文本 | 核适用范围后保留，禁止全局替换同名/同值 |

## 4. 与原有收工顺序衔接

完成适用文档联动、领域业务验证并记录缺口后，再按原流程分别 check structure/content/evidence、处理对应 BLOCK、seal、verify-sync；snapshot/handoff 仍单独判定。哈希、完整批次和接班观察不自动升级为业务一致。无法闭环时可保留有明确缺口标记的有效记忆批次，但交接必须列明待更新文件和影响，不能宣称全部同步或业务验收通过。

结果分别写“文档写入、回读、业务验证、在线同步、人员认领/交接”；不把其中一项当作整项完成。不同 Skill 复用同一交接结果，不重新分流、建库或重复 seal。仅本接口通过不代表原领域任务已完成。

## 5. 定期检查与自动化边界

默认没有后台巡检。用户要求定期检查时，复用已授权调度器或自动化任务，配置真实项目入口、检查范围、频率/时区、最近成功时间、报告去向和失败提示，并验证首次运行；缺调度器、连接或执行环境时明确未启用，先交付可审配置及缺口。用户未要求时只提出建议，不自行创建持续任务。

定期检查与发布前检查复用第2节，核对待同步项、事实/文档矛盾、旧来源及失效入口。结构化字段可用现有领域检查器；自然语言含义仍需阅读来源和业务判断。定时触发、依赖清单及同一任务源生成多视图只能减少遗漏，不能证明所有未知文档已覆盖。

## 6. 本接口的验证边界

改动维护规则后，用 [联动场景](../tests/document-consistency-cases.json) 交给独立观察者测试，先只提供 case 的 input，不提供 expected，再对照判定。保留原始意见、修订及未验证项。规则可读、文本保留检查与模拟场景不能冒充实际部署、跨平台写入或长期巡检效果；正式启用还需目标项目的真实变更及必要原有回归验证。
