# 监控窗口协议细则（独立窗口 · 有序进度播报）

适用：项目或实验正在长时间运行，用户希望在另一个窗口实时看到“按原编号顺序完成了什么、没完成什么、谁完成的、还等谁”，并能直接判断完成度的可信程度。

不适用：几分钟内结束的短任务，直接在聊天里给结果即可，不必开窗口。

## 角色与边界

| 角色 | 职责 | 边界 |
|---|---|---|
| 执行侧（主任务） | 跑任务、落盘进度与证据、维护核验表/状态文件、决定收口 | 不为播报修改实验口径 |
| 监控窗口（第二窗口） | 只读汇总与播报：读盘 → 按协议渲染 → 归档 | 除播报档案外不写文件；不操作实验环境；不替用户做待人工项；发现问题只报告不径自处理 |

监控窗口的服务对象是用户本人；它不承担执行职责，也不与执行侧互相覆盖文件。

## 启动三步

### 第 1 步：执行侧准备协议文件

在项目内写一份《监控窗口协议.md》（目录按项目规范，默认与核验表同处），至少包含：

- 顺序基准：核验表/任务清单路径（如 `三实验_原编号逐点核验表.csv`）；播报顺序一律按其中“原编号”，不重排。
- 进度数据源：状态 JSON、持续记录 jsonl、manifest、日志目录、进程；逐项说明“读什么字段、多久更新一次”。
- 证据根目录：截图、日志、结果文件所在目录及命名规则。
- 播报节奏：默认 15–30 分钟；训练类可改为“每轮完成后”；用户可指定。
- 收口条件、播报归档目录。

### 第 2 步：创建独立监控窗口

用户明确要求或同意后，用「新建任务」创建第二个窗口。监控任务书模板：

```text
【监控窗口任务书】
你是独立监控窗口，只读。
协议文件：<《监控窗口协议.md》路径>
职责：按协议读取数据源，按原编号顺序播报：
  1. 已完成 / 未完成（区分 ✅已核验 与 🟡待核验）
  2. 执行归属（人 / AI / 人+AI / 待人工）
  3. 待人工清单（需要本人做什么）
  4. 准确性提醒（证据缺失、陈旧、口径未确认）
边界：除播报档案外不写任何文件；不操作实验环境；发现问题只报告。
节奏：建立心跳自动化，每 <N> 分钟播报一轮；与上轮无变化时可压缩为简讯。
收口：收到执行侧完成信号或用户指示后，输出最终总表并停止心跳。
```

用户也可自行新开窗口后把协议文件路径发给它，效果相同。

### 第 3 步：设定时播报

- 首选：在监控窗口内建立心跳自动化，用自然语言说明频率（如“每 30 分钟按协议播报一轮”），由工具生成，不手写底层规则。
- 降级 1：环境不支持定时 → 执行侧在关键节点（阶段完成、失败、需要人工）向监控窗口发触发消息（需用户事先同意），窗口收到即播报一轮。
- 降级 2：完全无自动化 → 用户手动查看时触发；执行侧每完成一个阶段就把快照写盘，保证窗口“一打开就是最新”。
- 默认节奏：15–30 分钟一轮；训练类按“每轮完成”事件。与上轮完全无变化时可压缩成一行简讯，避免刷屏；用户要求“每次都完整”时照做。

## 数据源与顺序基准

顺序基准优先级（从高到低）：

1. 逐点核验表（“原编号”列）——最权威，含要求、执行者、完成判断等字段；
2. 任务书/讲义步骤清单；
3. 聊天记录里的步骤列表（仅兜底，注明来源）。

核验表常用列与播报字段的映射（以大数据治理运行材料为例，其他项目按实际列名对应）：

| 表字段 | 播报用途 |
|---|---|
| 原编号 | 排序与编号显示 |
| 要求 | 播报条目文本 |
| 状态 | 🔄/⬜/❌ 判断来源之一 |
| 实际执行者 | 归属标记（本人 / AI / 人+AI） |
| 本批证据 | 证据路径；缺失则不能标 ✅ |
| 完成判断 | 只把肯定验收值算完成 |
| 本人复做状态 | 含“待复做”时进入待人工清单 |

“待人工”的识别线索：实际执行者含本人/待填；触发条件含本人；类型为登录、身份验证、人工标注、GUI 操作、本人复做、最终上传等只能由人完成的动作；状态文件中的 blocked/handoff 字段。

没有核验表时：以任务书步骤为顺序，以结果文件/证据为唯一完成判据。

## 标记规范

状态（完成度 + 可信度）：

- `✅ 已核验`：完成且有可查证据（结果文件/截图/日志），且证据时间与本轮口径一致。
- `🟡 已完成待核验`：执行侧声称完成，但证据缺失、陈旧或口径未确认。
- `🔄 进行中`：有实际运行中的进程/任务。
- `⬜ 未开始`：未执行。
- `❌ 失败/阻塞`：失败、被终止或依赖阻塞。

归属：

- `人`：本人完成；`AI`：Codex 完成；`人+AI`：协作（条目内注明分工，如“本人登录，Codex 截图”）；`待人工`：等待本人执行。

证据：

- 每个 ✅ 至少指向一个证据（路径或目录）；同组证据可合并展示。
- 证据时间早于最近一次状态变更 → 标 `⚠️ 待复验`。
- 完成率默认按“已核验”口径统计，可同时给“含待核验”口径；未判定项不算入完成率。

## 播报模板

输出方式：每轮播报直接把播报内容作为 Markdown 消息发送，由聊天界面渲染（标题、列表、✅🟡 等标记正常显示）；不要把整份播报包进代码块或粘贴成纯文本。本节代码块仅用于展示模板结构。

```markdown
# 进度播报｜<项目/实验>｜<YYYY-MM-DD HH:MM>
数据源：<核验表>（读取时间 <t1>）；<状态文件>；<日志/进程>（检查时间 <t2>）

## 总览
- 已完成：<x>/<y>（已核验 <a> ｜ 待核验 <b>）
- 进行中：<c> ｜ 未开始：<d> ｜ 失败/阻塞：<e>
- 执行者分布：人工 <n1> ｜ AI <n2> ｜ 人+AI <n3> ｜ 待人工 <n4>
- 对照上次播报：新增完成 <k> 项、状态变化 <m> 项

## 按顺序完成情况

### <实验一>（原编号 1–98）
- ✅ #1–#6 人（证据：<目录>）
- 🟡 #7 AI —— 待核验：<原因>
- 🔄 #8（AI，运行中：<进程/任务>）
- 🙋 #9 待人工：<需要本人做什么，预计多久>
- ⬜ #10–#18

### <实验二>（原编号 1–57）
…

### <实验三>（原编号 1–76）
…

## 本轮变化
- 新增完成：#81–#96（AI；证据：<目录>）
- 状态变化：#54 🟡→✅
- 新增异常：<无 / 具体>

## 待人工清单（需要你处理）
1. #9 …：<一句话操作说明>（预计 <x> 分钟）

## 准确性提醒
- 🟡 待核验清单：<编号列表>（原因）
- ⚠️ 证据陈旧/待复验：<编号>（证据时间 <日期>）
- 不允许当作完成的内容：<计划、口头声明等>

## 结论
- 当前阶段：<…>
- 下一步：<…>
- 预计完成：<时间 / 待人工完成后确定>
```

## 压缩规则

- 相邻且“状态+归属”相同的项可以合并为一行，但合并行必须保留各项的要求名列表（可缩写成共同主题词+覆盖清单），状态说明可以共享一句；禁止只写编号或纯编号区间。
- 每一条都必须让读者看懂「要求是什么、已经做了什么」——条目格式：`标记 原编号「要求名」→ 已做/当前状态｜执行者`。
- `🟡`、`🔄`、`🙋`（待人工）、`❌` 永远逐项列出，不折叠。
- 每轮固定给出“待人工清单”和“准确性提醒”两个小节，即使为空也要写“无”。

## 收口

- 收口条件满足（或用户宣布停止）→ 监控窗口输出最终总表：全部条目按顺序完整列出一次（不再压缩），附证据索引与遗留问题，并停止心跳。
- 最终播报必须注明：哪些完成是“已核验”，哪些仍“待核验/待复做”，避免把运行中状态当成最终结论。
- 每轮播报追加归档到播报档案（如 `监控播报/播报_<YYYYMMDD_HHMM>.md`），这是监控窗口唯一的写入范围。

## 示例（节选）

```markdown
# 进度播报｜大数据治理三实验｜2026-10-12 14:30
数据源：三实验_原编号逐点核验表.csv（读取 14:29）；当前继续状态.json；训练_05 日志（检查 14:29）

## 总览
- 已完成：128/231（已核验 96 ｜ 待核验 32）
- 进行中：6 ｜ 未开始：89 ｜ 失败/阻塞：1
- 执行者分布：人工 8 ｜ AI 104 ｜ 人+AI 10 ｜ 待人工 6
- 对照上次播报：新增完成 18 项、状态变化 3 项

## 按顺序完成情况
### 实验一（原编号 1–98）
- ✅ #54–#70 人+AI（本人连接验证，Codex 执行截图；证据：实验一/03_截图/新版规则重做_20261012）
- 🔄 #71–#76（AI，平台重放同步运行中）
- 🙋 #97 待人工：学习通上传（最终定稿后执行）
…
```
