## 目标

把长任务从“开着终端盯输出”改成可恢复的后台协议：启动后通过 `process + log + result files + manifest` 四类信号判断是否健康，并在卡死或失败时按规则续跑；并可通过独立监控窗口向用户定时播报按原编号顺序的完成度、执行者归属与待人工清单。

## 核心原则

- 进度以结果文件和 manifest 为准，不以终端是否有输出为准。
- 每个 case 完成后立刻落 checkpoint。
- 卡死判定必须同时看进程存在、日志更新时间、结果文件增长和 running 状态持续时长。
- 自动重试必须有上限，超过后进入 hard failed，不要无限重启。
- 监控协议只负责托管，不修改实验口径。

## 标准状态

- `pending`：等待运行。
- `running`：当前正在运行。
- `completed`：结果文件存在且可读。
- `failed_retryable`：失败但可重试。
- `hard_failed`：超过重试上限或确定不可恢复。
- `stalled`：进程存在但结果/日志长期无变化。

## 标准工作流

1. 建 manifest：列出所有预期 case、目标结果文件、状态、重试次数、开始/结束时间、错误信息。
2. 启动 worker：用后台进程、计划任务或 chunk runner 执行少量 case。
3. wait 轮询：固定间隔读取 manifest、日志、结果目录、进程状态。
4. 健康判断：如果 completed 增长或日志更新，继续等待。
5. 卡死处理：如果 running 超过阈值且无结果/日志增长，停止 worker，把 case 回退为 retryable。
6. 续跑：优先 pending，再 failed_retryable；每次完成后写 checkpoint。
7. 收口：pending=0、retryable=0、running=0 后自动汇总；如有 hard_failed，生成失败清单。

## 独立监控窗口（第二窗口播报）

长任务运行期间，用户要求或同意时，为运行中的项目/实验另开一个独立监控窗口，定时播报“按原编号顺序完成了什么、没完成什么、谁完成的、还等谁”，让用户不盯着执行窗口也能直接看出整体进度和完成可信度。

最小流程：

1. 执行侧准备《监控窗口协议.md》：顺序基准（项目核验表/任务清单）、进度数据源、证据根目录、播报节奏、收口条件、播报归档目录。
2. 用户明确要求或同意后，用「新建任务」创建独立监控窗口；任务书包含协议路径、只读约束、播报模板。用户也可自行开窗口后把协议路径发给它。
3. 在监控窗口内建立心跳自动化实现“定时播报”；环境不支持定时时，退化为执行侧关键节点触发或用户手动查看。

硬性规则：

- 监控窗口只读：除播报档案外不写文件，不操作实验环境，不替用户执行待人工项，发现问题只报告。
- 播报必须区分 `✅已核验` 与 `🟡待核验`；证据缺失、证据陈旧或口径未确认的项不能标 ✅。计划、声明、聊天记录里的“已完成”不构成完成证据。
- 每轮播报固定包含：总览统计、按原编号顺序清单、本轮变化、待人工清单、准确性提醒。
- 播报直接以渲染后的 Markdown 输出（正常消息，不包代码块或纯文本粘贴）。
- 播报条目必须写清「要求是什么」和「已经做了什么」；禁止只给编号或纯区间，压缩合并时各项要求名仍须可见。
- 待人工、进行中、失败项永远逐项显示；只有相邻 `✅`/`⬜` 可以压缩成区间行。

完整细则、播报模板、标记规范和降级路径：`references/monitor-window-protocol.md`。

## 默认阈值

- 短任务 smoke：`waitInterval = 30s`，`stallMinutes = 10`。
- 中等任务：`waitInterval = 60s`，`stallMinutes = 30`。
- 高维/昂贵任务：`waitInterval = 300s`，`stallMinutes = 120`。
- 单 case 最大重试：`maxRetries = 3`。

实际使用时按任务平均耗时调整，不能把合法慢任务误杀。

## 输出要求

每次建立监控协议时，输出：

- 任务范围和总 case 数。
- 启动命令。
- manifest/checkpoint 路径。
- 日志路径。
- 结果目录。
- 卡死判定阈值。
- 自动恢复策略。
- 最终完成条件。
- 手动查看进度命令。
- 若启用监控窗口：协议文件路径、窗口创建方式、播报节奏与收口条件。

## 风险边界

- 不要在未确认目标路径时递归删除文件。
- 不要把所有失败都自动重试到死。
- 不要用进程存在作为“正在正常跑”的唯一证据。
- 不要在实验口径未冻结时启动整夜任务。
- 如果用户明确要求不代跑，只生成监控协议和命令，不启动任务。
- 不要把播报做成执行：监控窗口只报告，处置仍归执行侧或用户。
- 不要用聊天声明或计划条目充当完成证据；`✅` 必须有当前口径下可查的落盘证据。

## 任务终态资源回收

执行侧在`finally`关闭本轮内核/模型子进程、IPC句柄和临时浏览器，必要时join/wait核对真实退出；以PID加命令行/任务标识确认所有权，不能按进程名或复用PID结束其他聊天、MCP服务、用户虚拟机/应用。监控窗口仍只报告，不自行越权终止进程。保存必须留存的结果/诊断后，结束只为本任务开启的监控器；失败或取消也按允许范围做同样收口。

文件清理在验收与消费者结束之后交给[artifact-curator精确清单流程](../artifact-curator-zh/references/experiment-closeout.md)，临时验证用完即回收，不保留多份全量工作目录。进程退出、逻辑文件删除量与系统可用内存分别记录；无法确认退出时保留现场，不先删其输入。
